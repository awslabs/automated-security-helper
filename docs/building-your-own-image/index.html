    Building your own container image

    ASH does not publish a container image to a public registry, and is not planning to. The recommended posture is that the organization running ASH builds the image and hosts it in its own registry.

    Why you build it yourself

    ASH reads your source code. An image that scans your repositories sits in the same trust position as your build tooling, so the question "what is in this image, when did it change, and who approved that change" needs an answer that belongs to you rather than to an upstream publisher.

    Building it yourself gives you four things a pulled public image cannot:

    • A known provenance. The image came from a Dockerfile in a commit you can name, built by a pipeline you control.
    • A patching cadence you set. You decide when the base image and the bundled scanner tools move, rather than inheriting whenever an upstream tag was pushed.
    • A scanning surface you can inspect. The image can be scanned, signed, and admitted by the same controls you already apply to your own images.
    • No new external dependency at scan time. Your CI pulls from your registry, so a scan does not fail because a public registry is unavailable or rate-limited.

    The tradeoff is real and worth stating plainly: you own the rebuild cadence. An image built once and never rebuilt ages, and ASH's bundled scanners age with it. See Keeping it current.

    Build it once, host it internally

    # Build the image
ash build-image --build-target non-root

# Tag and push to your own registry
docker tag automated-security-helper:non-root \
  my-registry.example.com/security/ash:3.6.0
docker push my-registry.example.com/security/ash:3.6.0

    Two build targets exist:

    Target Runs as Use when
    non-root An unprivileged user The default. Prefer it.
    ci Root The runner's UID/GID mapping makes an unprivileged user impractical

    non-root is the default everywhere except Windows. On Windows, container mode (ash --mode container, Invoke-ASH) and ash build-image default to the ci stage, because the output directory is bind-mounted and the runtime there does not map write permissions onto that mount, so the non-root user could not write its reports and logs. Pass --build-target non-root (-BuildTarget non-root) to build the unprivileged image on Windows anyway. Running in CI does not change the default: CI, IsCI, ISCI and CODEBUILD_BUILD_ID play no part, and an explicit --build-target always wins. The stage name is read in any case, as the build reads it: NON-ROOT is non-root, and is built, tagged and checked as non-root. --custom-containerfile builds on ci; with it, --build-target non-root names the custom file's own non-root stage (see Extending the image).

    The non-root stage creates its user with the UID and GID of the account running ASH, or with --container-uid and --container-gid. A UID of 0 is root and cannot be that user, and a GID of 0 is root's group, so a non-root build with UID 0 or GID 0 is refused before anything is built, and so is a UID or GID that is not a number. That is the case when ASH itself runs as root, as many CI jobs do (AWS CodeBuild, container-based GitLab and Jenkins jobs): pass --build-target ci there. Another --container-uid and --container-gid work only when the output directory is writable by that UID, since the container runs as that user and writes its reports there; on a root host ASH creates the output directory as root. ./ash refuses it the same way, and so does Invoke-ASH, run as root or given -ContainerUID 0 or -ContainerGID 0; its opt-in is -BuildTarget ci. On Linux and macOS, Invoke-ASH gives the non-root user the caller's own UID and GID (id -u, id -g) unless -ContainerUID or -ContainerGID names another, as ./ash and ash --mode container do, and checks both the same way; on Windows the Dockerfile's defaults apply.

    The opt-in for a job that runs as root, such as an AWS CodeBuild build:

    ash --mode container --build-target ci        # or: ./ash --build-target ci

    Invoke-ASH -BuildTarget ci

    Point ASH at your published image with ASH_IMAGE_NAME:

    export ASH_IMAGE_NAME="my-registry.example.com/security/ash:3.6.0"
ash --mode container --source-dir .

    Tag with the ASH version you built rather than only latest, so a scan result can be traced back to a specific image. A moving latest makes two scans that disagree impossible to explain.

    The image's ASH must be the same version as the ASH that runs the scan, or later. Container mode reads the scan's results back only when the ASH in the image records that its run completed, which ASH v3.7.1 and earlier do not do. With an image built from an older ASH, every container scan exits 1 with an error saying the inner run did not complete. Rebuild and republish the image when you upgrade the ASH that runs your scans.

    Who can write to the image's directories

    Who owns each of the image's directories, and who else may write it:

    Directory Owner Why
    /deps, /deps/.semgrep, /deps/.opengrep (offline rules), /ash, /.ash/bin (bundled tools, first on PATH) root, not writable by others Nothing writes there at scan time
    /deps/.grype (grype's database), /deps/.trivy (trivy's cache, TRIVY_CACHE_DIR) the user the image runs as: root in ci, the unprivileged user in non-root; root in an offline image grype's and trivy's database updates write them at scan time; an offline image never updates them
    /src, /out writable by every user, with the sticky bit (ci); the unprivileged user (non-root) A run mounts the source and the output here; without those mounts, these two stay writable when the ci image is started under another UID (the database caches do not, see below)

    Outside /src, /out and the sticky scratch directories (/tmp, /var/tmp, /run/lock), nothing in the image is writable by every user. Each stage ends by clearing group and other write on anything an installer left that way, such as the lock files uv creates mode 666 in its cache and tool directories and the files some gems ship mode 777 under /var/lib/gems.

    An image you extend with --custom-containerfile keeps these modes unless your Dockerfile changes them.

    Because only its own user may write the grype and trivy database caches, an image started under a different UID than the one that owns them cannot update the databases: grype or trivy then reports ERROR and the scan fails, rather than scanning against a database it could not refresh. In a non-root image that owner is the UID it was built with (--container-uid, or the host's); in ci it is root, so a ci image has to run as root, which is how ASH's own runner starts it. Build a non-root image with the UID it will run as, or use ci and run it as root. A platform that starts every container under a UID of its own needs an image built for that UID.

    Which Dockerfile ASH builds

    ash build-image and ash --mode container build ASH's own Dockerfile. They never build a Dockerfile found in the directory you run them from or in a directory above it: that file belongs to the project being scanned. Which of ASH's Dockerfiles is used depends on how ASH was installed:

    • Installed from a git URL or a package index. The Dockerfile packaged with ASH, which installs the same ASH revision from git inside the image (--ash-revision-to-install picks another one).
    • Installed from its source tree (an editable install, or pip install <dir> or uvx --from <dir>; the revision is LOCAL). The Dockerfile at the root of that source tree, with the tree as the build context. ASH finds the tree from where the running package is installed, so ash run from a subdirectory of the checkout, or from another project, builds the same image. A package an installer put in a site-packages directory, with its dist-info beside it, is never taken for a clone, whatever other files sit next to it.

    A LOCAL revision for an installation with no source tree beside it or recorded for it (for example, ASH installed from a wheel file) is refused before anything is built. Pass --ash-revision-to-install <tag>, reinstall ASH from its source directory, or run an image you already have with --no-build.

    Which ASH goes into the image

    The image installs ASH from source. Which source depends on how the ASH that runs the build was installed:

    ASH running the build Source of the image's ASH
    A clone of the ASH repository, an editable install of one, or pip install <directory> That source tree, the same ASH as the one running. If the directory has since been deleted, or no longer holds ASH's source, the image installs the commit the package build recorded, as in the last row. The directory is trusted by its path, so install from one only you can write, not from under /tmp.
    From a git URL with a tag or a branch, such as @v3.7.0 or @main That tag or branch of the ASH repository on GitHub, cloned during the build. A git+file:// URL is no different: its ref is cloned from GitHub, not from the repository the URL names.
    From a git URL with no ref The installed commit, checked out of a clone of the ASH repository on GitHub.
    Anything else: Homebrew, a wheel or sdist file, an archive URL The commit the package was built from, checked out of a clone of the ASH repository. A package build records it when it runs in a git checkout of ASH. With none recorded (a build from a source tarball), the release tag of the installed version, such as v3.7.0, and a warning that this is a guess: a build of an unreleased commit carries the version of the release before it.

    A development or pre-release version has no release tag, so with nothing recorded the build stops before it starts and asks for --ash-revision-to-install. That option overrides the table: pass a tag, a branch, or a full 40-character commit id. --ash-revision-to-install LOCAL builds the running ASH's own source tree, and is refused when there is none, for example for a wheel install.

    A commit id, given or recorded, is built only if a branch or a tag of the ASH repository reaches it. Otherwise the Dockerfile's clone step stops with exit status 3, the image build fails, and ash exits with the build's status (1 for a failed docker build). Every branch counts, the ones GitHub and its apps create included, such as the merge queue's gh-readonly-queue/*, Dependabot's dependabot/* and gh-pages, and so does every tag; a pull request's ref (refs/pull/*) does not. GitHub serves a commit that only a fork or a pull request holds under the ASH repository's URL as well, so the id alone does not show that the commit is ASH's. A package built from a commit that is on no branch or tag there yet, a local one for example, records that commit: run the ASH installed from that source tree with --ash-revision-to-install LOCAL, or name a branch instead.

    Container mode and ash build-image never build a Dockerfile from the working directory, which is usually the project being scanned. A LOCAL build uses the ASH source tree above, and any other revision uses the Dockerfile packaged with ASH, which clones that revision. ASH v3.0.1 to v3.7.1 could build a Dockerfile they found in or above the working directory and tag the result as ASH's image (automated-security-helper:<target>, or your ASH_IMAGE_NAME), and --no-build runs whatever image has that tag. If you ran one of them in or under a project with its own Dockerfile, remove that image, run ash build-image --force, and push again any copy you host in a registry.

    A build whose context is ASH's own source tree builds that tree, whatever the revision. ./ash always builds its own checkout, and the image pipelines under deploy/ build the clone they check out.

    A branch, or the floating v3 tag, is cloned again on every build, because it can have moved since the last one. A release tag or a commit id is cloned once, and later builds take that clone from the build cache.

    Keeping it current

    ASH orchestrates external scanners, and their versions are not all pinned. A rebuild can therefore change which findings you get, in both directions — a scanner release can add checks or drop them. cfn-nag is one that is pinned: the image installs it and every gem it depends on from the committed automated_security_helper/assets/Gemfile.lock, with Bundler frozen, so each build of one ASH version installs the same gems. A build whose Gemfile and Gemfile.lock disagree fails at that step instead of resolving new versions. That is an argument for rebuilding on a schedule you choose and reviewing the delta, not for rebuilding as rarely as possible.

    A workable cadence:

    • Rebuild when you upgrade ASH, and tag the image with that ASH version.
    • Rebuild on a fixed interval regardless, so base-image CVE fixes land.
    • Compare a scan of a known repository across the old and new image before promoting the new one. A jump in finding counts is usually a scanner version change rather than a change in your code.

    Air-gapped and offline builds

    Building with --offline caches the tool vulnerability databases into the image itself, so a scan needs no network access:

    ash build-image --build-target non-root --offline

    The build itself still requires network access — that is when the dependencies and databases are fetched. The image keeps trivy's database in TRIVY_CACHE_DIR (/deps/.trivy) and the cfn-guard rules in ASH_CFN_GUARD_RULES_DIR (/usr/share/ash/cfn-guard-rules, owned by root). Only the resulting scan is offline. An offline image's databases are frozen at build time, which makes the rebuild cadence above load-bearing rather than optional.

    npm-audit has no database to cache: npm, yarn and pnpm audit a lockfile by asking the registry, so an offline image cannot run it. A scan with the image reports npm-audit MISSING, and exits 1, for a project that has a package-lock.json, npm-shrinkwrap.json, yarn.lock or pnpm-lock.yaml beside a package.json, and SKIPPED for one that has none. Add --exclude-scanners npm-audit to the scan command to scan such a project with the offline image.

    An offline image stops passing once grype's database or its rulesets are past their bound. ASH reads each database's own build time after the scan and holds it to a bound: trivy's database 24 hours after it was published, which is trivy's own rule, grype's database 5 days (120h) after it was built, which is grype's own default, and the offline semgrep and opengrep rulesets 30 days after they were downloaded (the build records that time in .ash-rules-fetched-at). Past grype's or a ruleset's bound the scan exits 1. This applies in offline mode exactly as online; before it, an offline scan with a weeks-old database exited 0 with no warning.

    trivy's database is the exception. Its bound would fail every trivy scan in the image from a day after the build, so an offline image holds it to warn instead: past 24 hours the scan still passes, and the summary reports, ash.sarif and ash.flat.json all say the trivy database was stale, how old it was, and that the offline image's default let the scan pass. To make it fail the scan in the image too, set content_db_staleness_offline_image_default: false in the ASH config or pass --no-allow-stale-content-db.

    A stale trivy database still lacks every advisory published since the build, so refresh the image anyway. Rebuild it with ash build-image --offline, which downloads current databases and rulesets, and move the new image across the air gap: at least every 5 days to keep grype's scans passing (every 30 days, for the rulesets, with scanners.grype.enabled: false), and as often as you want trivy's findings current. Without --force, a build upgrades the OS packages and, offline, downloads a current grype database and current rulesets once per UTC day; with it (--force is --no-cache), on every build. The same holds for ./ash and Invoke-ASH, online or offline. Rebuilds later the same day come from the build cache. The first one on a new day re-runs the Dockerfile's core stage from its apt-get upgrade step down (the OS packages, the scanner tools, the ASH package and, offline, the download), so it needs network access.

    On the air-gapped host, scan with the image you moved there instead of rebuilding it: ash scan --mode container --offline --no-build, ./ash --offline --no-build, or Invoke-ASH -Offline -NoBuild. Container mode builds the image before every scan unless told not to, and a build on a new day needs network access. The image has to carry the name ASH runs, automated-security-helper:<build target>, or the one ASH_IMAGE_NAME names.

    A docker build of the Dockerfile run by hand gets the same result by passing OFFLINE=YES and, as BUILD_DATE_EPOCH, UTC midnight of the day in epoch seconds: now=$(date +%s); docker build --build-arg OFFLINE=YES --build-arg BUILD_DATE_EPOCH=$((now - now % 86400)) .... Pass BUILD_DATE_EPOCH for an online build too. Without a new value the apt-get upgrade step and the download step are served from the build cache, with the OS packages and databases they held then.

    To scan with an image older than that anyway, pass --allow-stale-content-db or set content_db_staleness: warn; the scan passes, and the same reports say which databases were stale and how old they were. See Failing on a stale content database.

    If you would rather not run a container

    --mode local runs ASH as a Python process with no image involved:

    uvx git+https://github.com/awslabs/automated-security-helper.git@v3.7.0 --mode local --source-dir .

    This avoids the image question entirely, at a cost: a few of the tools ASH orchestrates cannot be installed through Python packaging alone, so local mode runs a smaller set of scanners than container mode. Check the scanner table in the run summary to see which ones participated rather than assuming parity.

    If you build per run in CI

    Building on every run is supported and is the simplest thing that works, but it is the slowest. On GitHub Actions, ASH passes --cache-from/--cache-to type=gha automatically when ACTIONS_CACHE_URL or ACTIONS_RESULTS_URL is set, with a separate cache scope per build target, so a warm cache skips most of the build. Nothing needs configuring for that.

    Even with caching, a registry-hosted image is faster and gives you the provenance story above. Per-run builds are best treated as a starting point rather than a destination.

    Extending the image

    --custom-containerfile builds your own Dockerfile on top of ASH's, with the ASH image passed in as the ASH_BASE_IMAGE build argument:

    ash build-image --build-target ci --custom-containerfile ./Dockerfile.internal

    Supplying a custom containerfile builds ASH's image at the ci target, so the run-as-non-root configuration is not applied. Securing the final image is then yours to do — set a non-root USER in your own Dockerfile if you need one. To build that, give your Dockerfile a stage named non-root (FROM ${ASH_BASE_IMAGE} AS non-root, followed by the USER it should run as) and pass --build-target non-root: ASH builds its own image at ci and your file at its non-root stage. --build-target non-root with a custom Dockerfile that has no such stage is refused with exit 3 before anything is built, since the image would otherwise run as root without a word.

    Third-party license files in the image

    The image bundles third-party programs that ASH installs from their upstream releases: actionlint, cfn-guard (with the AWS Guard Rules Registry it reads), gitleaks, grype, opengrep, syft, trivy and uv today, and the Python scanners bandit, checkov, cfn-lint, semgrep and zizmor (installed with uv tool install). Each one's license and notice files are in the image under /usr/share/doc/ash/third-party/<tool>/, taken from the exact release the image carries. Beside them, a SOURCE file names the upstream repository, release tag and commit. For a copyleft tool (opengrep is LGPL-2.1), that file also says where the corresponding source is.

    /usr/share/doc/ash/third-party/index.json lists every bundled tool with its version, license expression, repository, commit and files. The image build writes it only after checking every entry against the built image, so it describes what is actually installed.

    docker run --rm automated-security-helper:non-root cat /usr/share/doc/ash/third-party/index.json

    If you redistribute the image, these are the files that go with those programs. Packages installed from Debian carry their own copyright files under /usr/share/doc/<package>/, and Python packages carry their license metadata in their .dist-info directories.

    Configuration Guide

    ASH v3 uses a YAML configuration file to control its behavior. This guide explains how to configure ASH for your project.

    Configuration File Location

    ASH reads its configuration from one source. When --config (or the ASH_CONFIG environment variable) names a file, that file is used. Otherwise ASH looks in the source directory in this order and uses the first source it finds:

    1. .ash.yml
    2. .ash/.ash.yml
    3. .ash.yaml
    4. .ash/.ash.yaml
    5. .ash.json
    6. .ash/.ash.json
    7. ash.yml
    8. .ash/ash.yml
    9. ash.yaml
    10. .ash/ash.yaml
    11. ash.json
    12. .ash/ash.json
    13. .ashrc.toml
    14. .ashrc.yaml
    15. .ashrc.yml
    16. .ashrc.json
    17. ashrc.toml
    18. ashrc.yaml
    19. ashrc.yml
    20. ashrc.json
    21. pyproject.toml

    Items 1-12 are checked per filename, not per directory: for each name ASH checks the source directory and then its .ash/ subdirectory, so .ash.yml in the source directory beats .ash/.ash.yaml. Items 13-21 are checked in the source directory only. A pyproject.toml counts only when it has a [tool.ash] table; one without that table is not a config source. The lists come from ASH_CONFIG_FILE_NAMES, ASH_RC_FILE_NAMES and ASH_PYPROJECT_FILE_NAME in automated_security_helper/core/constants.py.

    Sources are never merged. If more than one exists, ASH logs which one it used and logs a warning naming each one it ignored, once. The scan repeats each of those warnings under "CONFIGURATION WARNING" in its summary and records it in the results as a config_warning entry of validation_checkpoints, because the settings in an ignored source are not applied; ash merge keeps one copy of a warning every shard recorded. The names in items 1-12 are deprecated in favor of an ashrc file or [tool.ash], and the warning says so when one of them shadows a newer source. They still take precedence, so adding a [tool.ash] table to a repository that already has .ash/.ash.yaml does not change which settings a scan uses until the older file is removed.

    Scan results are written to .ash/ash_output whichever source is used.

    You can also specify a custom configuration file path using the --config option:

    ash --config /path/to/my-config.yaml

    In a single-directory scan, that file replaces discovery, so the repository's own config is not read. In workspace mode (ash --workspace) it is layered over each project's own config instead: every field it sets is final for every project, and a project's config fills only the fields it leaves unset. See The operator's config.

    A config file that cannot be loaded stops the scan

    ASH uses its built-in default configuration only when there is no config file at all: none named and none found in the source directory. A config file that is named or found and cannot be loaded stops the scan with exit code 3 before any scanner runs, and the message names the file. That covers:

    • a file named by --config, ASH_CONFIG, the config argument of run_ash_scan() or an MCP tool's config_path that does not exist, and an empty --config "". An empty ASH_CONFIG counts as unset;
    • a named or discovered file that is not valid YAML, JSON or TOML, is not UTF-8, cannot be read, is larger than 1 MiB, uses a YAML alias (*name), or is a directory, FIFO, device or other non-regular file. A syntax error, and an alias, names its line. A file that is not a regular file is refused without being read, so a FIFO or /dev/zero at a config name does not stall the scan. A leading UTF-8 byte order mark is accepted in YAML, JSON and TOML alike. Aliases are refused in every YAML ASH reads as configuration (config files, extends bases, workspace policy files, MCP profiles and a client's override_yaml), because a few hundred bytes of nested aliases expand to gigabytes when the config is written into the results; an anchor (&name) that nothing refers to is accepted;
    • a dangling symbolic link at one of the names above, for example .ash/.ash.yaml linked to a shared file that is not checked out. It is not treated as "no config";
    • a pyproject.toml that cannot be read at all, when it would be the source ASH uses: ASH cannot tell whether it holds a [tool.ash] table;
    • a config name ASH cannot look for, such as one inside an .ash/ directory that cannot be searched: ASH cannot tell whether the file is there.

    Scanning with the defaults instead would run without the file's suppressions, ignore paths, thresholds and sandbox settings, and report the scan as completed. The same applies to ash report, ash plugin list, ash dependencies install, ash config get and ash config wizard (each exits 3; the wizard leaves the file as it was rather than rewriting it from the defaults), to workspace mode (see Workspace mode), and to the MCP server: scan_directory refuses such a file, and an empty config_path, before it starts a scan, a workspace scan's session profile that does not load is reported as an invalid configuration (exit code 3), and get_config (with or without raw) returns an error instead of the default configuration, with error_category file_not_found for a file that does not exist and invalid_format for one that does not load. A config file outside the session's allowed config roots is refused as outside them before anything reads it, so the response says nothing about its contents. That includes a config source found in the scanned directory: a pyproject.toml, a config file or an .ash/ directory that is a symbolic link out of the roots is refused before discovery opens it, with the same response whether its target is missing, unreadable or readable.

    Configuring ASH in pyproject.toml

    [tool.ash] holds the same settings as .ashrc.yaml, written as TOML, and is validated by the same schema:

    [tool.ash]
project_name = "my-service"
fail_on_findings = true

[tool.ash.global_settings]
severity_threshold = "MEDIUM"
ignore_paths = [{ path = "tests/fixtures/**", reason = "Test fixtures" }]

[[tool.ash.global_settings.suppressions]]
rule_id = "B101"
path = "tests/**"
reason = "assert is expected in tests"

[tool.ash.scanners.bandit]
enabled = true

    A validation error names the table and its line, for example pyproject.toml [tool.ash] (line 12). String values beginning with ${ are resolved from the environment by the same rule as in YAML, including the limit on which variable names may be read; see the !ENV notes in Configuration Overrides. ash config update, ash config wizard, ash config lint --fix and the suppression dialog in ash inspect edit YAML and JSON (a .json config is written back as JSON), so they refuse a TOML file rather than rewrite it; edit [tool.ash] by hand.

    A pyproject.toml that is not valid TOML is skipped, unless its text declares a [tool.ash] table, in which case the scan fails instead of running with the default configuration. One that cannot be read at all (a dangling link, no permission) fails the scan when it would be the source ASH uses; behind a higher-precedence file it is only logged.

    Creating a Configuration File

    The easiest way to create a configuration file is to use the config init command:

    ash config init

    This creates .ashrc.yaml in the current directory with every setting at its default. It is one of the newer names discovery reads (items 13-21 above), so its discovery warning does not apply to it. When the directory already has a config source, such as .ash/.ash.yaml or a [tool.ash] table, ash config init refuses instead of adding a second one, because sources are never merged; keep using the existing file, or pass --config to write somewhere else. Existing files under the older names keep working. ash config wizard without --config edits the config a scan would use, or creates .ashrc.yaml, and ash inspect findings saves suppressions to .ashrc.yaml when there is no config yet.

    Configuration Structure

    The ASH configuration file has the following main sections:

    # yaml-language-server: $schema=https://raw.githubusercontent.com/awslabs/automated-security-helper/refs/heads/main/automated_security_helper/schemas/AshConfig.json
project_name: my-project
global_settings:
  severity_threshold: MEDIUM
  ignore_paths: []
fail_on_incomplete_scanners: true
converters:
  # Converter plugins configuration
scanners:
  # Scanner plugins configuration
reporters:
  # Reporter plugins configuration
output_formats: []  # Empty writes every enabled reporter
ash_plugin_modules: []

    Naming the project

    project_name names the project in the reports: the HTML, Markdown and text reports, metadata.project in ash.flat.json, metadata.project_name in ash_aggregated_results.json, and the SPDX document's root package. Without it the name is the ASH_PROJECT_NAME environment variable, else ash-scan. In workspace mode each project's reports carry that project's label instead.

    Failing on an incomplete scan

    fail_on_incomplete_scanners is a top-level key, and it is on by default. ASH exits 1 when a scanner you selected did not complete — status ERROR (it ran and failed) or MISSING (its dependencies were unavailable, so it never ran) — and prints which ones.

    It is on rather than off because a scanner recorded ERROR or MISSING produces no findings, so with the gate off that scan reports the exit code of a clean one. That is the one failure a reader cannot see: the crash is visible in the log, the false all-clear is not. A host that genuinely cannot provide a scanner's tool says so once, with the key below or --no-fail-on-incomplete-scanners, and keeps its old exit codes.

    It selects on status, so it covers a failure only once that failure has reached the status. A tool's own failure does reach it: a scanner whose tool exits with a code outside the codes that scanner accepts for a completed run is ERROR, whatever its results file holds, and the row records the exit code and the tool's stderr. A failed tool can still leave a results file behind (semgrep writes SARIF holding only error notifications when it cannot read its rules, grype a zero-byte report when it cannot load its database), and "found nothing" and "never scanned" look the same in it, so that file is not read. The accepted codes per scanner are in Scanner exit codes. A results file ASH cannot read as SARIF is ERROR too, whatever the exit code, as is an empty results file, SARIF with no run, and a scanner result that carries nothing to grade (a dict with no status, severity_counts or findings, a dict whose status does not say its tool completed, or a list or string from a scanner's own scan()); none of them can show that the target is clean. The scanners ASH ships write SARIF with one run even when there is nothing for them to scan. So is a scanner whose tool reports that its content database does not exist; see Failing on a stale content database.

    With the key off, an ERROR scanner no longer fails the scan: the exit code comes from the findings alone, so a scan whose only problem is a failed scanner exits 0, the same code as a clean scan. That is what turning the gate off means, and the summary table still shows the ERROR row.

    It covers converters too: a converter that crashed, one that could not convert some of its inputs (converter_results.<name>.failed_inputs), and one whose tool is missing while it had inputs make the scan exit 1, as an incomplete scanner does, in ash merge and per project in workspace mode as well.

    SKIPPED scanners are ones you did not select and never trip it, which is what keeps a sharded scan working: each shard excludes the scanners its siblings own, and those are recorded as SKIPPED. Narrowing a run with --scanners, --exclude-scanners or --python-only also records the scanners you left out as SKIPPED, whether or not their tools are installed, so selecting a subset does not fail the gate.

    A scanner with nothing to scan in the project is SKIPPED too, whether or not its tool is installed: cdk-nag and cfn-nag when no scanned file is a CloudFormation template, npm-audit when no package.json has a lockfile (package-lock.json, npm-shrinkwrap.json, yarn.lock or pnpm-lock.yaml) beside it. A JSON or YAML file ASH cannot read counts as a possible template. A file that does not parse as a template is read again with unknown YAML tags and JSON comments allowed, and counts when that yields a document with Resources, or when its text contains AWSTemplateFormatVersion or a Type: AWS:: resource type, as a damaged template does. So an mkdocs.yml with !!python/name: tags, a Helm chart's templates and a tsconfig.json with comments leave cdk-nag and cfn-nag SKIPPED, as they do with the tools installed, and a truncated template leaves them MISSING. A scanner that has files to scan and no tool is still MISSING, and still fails the gate. The row's skipped_reason or missing_reason in ash_aggregated_results.json says which.

    To accept a partial scan's exit code, set it to false:

    fail_on_incomplete_scanners: false

    Prefer excluding the scanner whose tool you do not have. false makes ASH exit 0 for a scan where nothing ran, which is the same code as a scan where everything ran and found nothing; excluding the scanner records it as SKIPPED and says so in the report, so the next reader can see what was and was not measured.

    It is independent of fail_on_findings in both directions. fail_on_findings: false still reports an incomplete scan, and when both would fail the exit code is 1 rather than 2, because clearing the findings that were reported would not make the scan complete. See An incomplete scan is not a clean scan.

    Failing on a stale content database

    content_db_staleness is a top-level key, and it defaults to fail. After each scanner that matches against a content database, ASH reads that database's own build time and compares it to the bound declared for it in automated_security_helper/utils/content_databases.py. Past the bound, the scan exits 1 and names the database, when it was built, how old it is, the bound, and how to refresh it. This happens in online and offline mode alike.

    Database Scanner Bound Where the bound comes from Age read from
    grype-db grype 120h (5 days) grype's own default, db.max-allowed-built-age built in grype db status -o json
    trivy-db trivy-repo, unless its scanners list leaves out vuln, and trivy 24h trivy's own rule: a database is current until its NextUpdate, which the published database sets 24h after UpdatedAt VulnerabilityDB.UpdatedAt in trivy version --format json
    semgrep-offline-rules semgrep (offline only) 720h (30 days) ASH's own choice; semgrep has no staleness notion for local rules .ash-rules-fetched-at in $SEMGREP_RULES_CACHE_DIR, else the oldest rules file's mtime
    opengrep-offline-rules opengrep (offline only) 720h (30 days) ASH's own choice; opengrep has no staleness notion for local rules .ash-rules-fetched-at in $OPENGREP_RULES_CACHE_DIR, else the oldest rules file's mtime

    A database whose build time cannot be read is treated as stale, because an unmeasurable database is not evidence of a fresh one. So is a database whose build time is more than 15 minutes ahead of the host's clock: its age cannot be measured, and the message says so.

    A database the tool reports does not exist at all (grype's database does not exist, no VulnerabilityDB from trivy, no rules files in the offline rules directory) also makes that scanner ERROR, under fail and warn alike: the scan had nothing to match against, so its zero findings are not a result. warn relaxes the age bound for a database that exists.

    Under fail, a scanner whose result is clean and whose database is stale is recorded ERROR, not PASSED, in its scanner row, ash.flat.json and the summary table, with the stale database named. A scanner that found something keeps FAILED, because its findings are real. The scan reports that ERROR once, as the stale database with how to refresh it: it is not listed again as an incomplete scanner, it counts as a scanner that ran, and ash merge merges its shard and then exits 1 on the stale database.

    To let one scan run against a stale database, pass --allow-stale-content-db, or set:

    content_db_staleness: warn

    Under warn the scan proceeds, and the warning is written to the log and into the reports: a ### Stale content databases section in ash.summary.md, a STALE CONTENT DATABASES section in ash.summary.txt, a toolConfigurationNotifications entry with descriptor id ASH-CONTENT-DB-STALE on the scanner's invocation in ash.sarif, and a content_databases list in ash.flat.json with stale: true and enforced: false. A reader of any of those can see the scan ran against an out-of-date database.

    To relax one database without relaxing the others, for example while an upstream publisher is not publishing, name it in content_db_staleness_overrides:

    content_db_staleness: fail
content_db_staleness_overrides:
  - database: trivy-db        # a name from the table above
    policy: warn
    expiration: "2026-10-11"  # YYYY-MM-DD; required
    reason: "Upstream trivy-db publishing is failing"  # required

    The entry applies only to the database it names, so every other database is still held to content_db_staleness. It stops applying at 00:00 UTC on its expiration date: from then on it is ignored, with a warning in the log, and the database is held to the policy it has without the entry. That is content_db_staleness, except for trivy-db in an image built with OFFLINE=YES, which returns to that image's warn default described below. A stale database relaxed this way is reported the same as under warn, and the message names the entry and its expiry. Each database can appear in at most one entry, and an unknown database name is a config error. The list is empty by default.

    An image built with OFFLINE=YES (ash build-image --offline) holds trivy-db to warn rather than to content_db_staleness: fail. The image carries the trivy database it was built with, and the 24h bound would otherwise fail every scan in it from a day after the build. So those scans pass, and each report records the stale database as it does under warn, with a message saying the offline image's default let the scan pass. Only trivy-db is relaxed: grype-db and the offline rulesets still fail the scan once they are past their bounds. What turns this on is ASH_OFFLINE_AT_BUILD_TIME=YES in ASH's environment, which the image sets from its OFFLINE build argument and nothing else in ASH sets; the config cannot turn it on, and a process given that variable some other way gets the same default. To hold trivy-db to content_db_staleness in the image as well:

    content_db_staleness_offline_image_default: false  # default true

    A content_db_staleness_overrides entry for trivy-db outranks this default, and once the entry expires the database returns to it.

    The CLI flag takes precedence over the config value in both directions: --no-allow-stale-content-db restores fail for one scan even when the config says warn, and either form of the flag also clears content_db_staleness_overrides and sets content_db_staleness_offline_image_default to false for that scan, so it decides for every database, trivy-db in an offline image included. Like fail_on_incomplete_scanners, none of these keys can be changed by an MCP runtime patch.

    Relaxing the check is the operator's choice. Set warn, or an entry with policy: warn, with the flag, --config-overrides or a config file outside the scanned tree. From a config file inside the tree (a repository's .ash/.ash.yaml, or a workspace project's own config) they are ignored with a warning naming the key, unless they equal the operator's value. fail, and an entry with policy: fail, only make the check stricter, so they apply from any config. See Settings a repository's config cannot choose.

    This gate is independent of fail_on_incomplete_scanners and does not need it turned on. When the scan also has actionable findings, the exit code is 1 rather than 2: clearing the reported findings would not make a scan against a stale database trustworthy.

    Ignore files and the scan set

    Before the scanners run, ASH builds a scan set: the list of files in the source directory that detect-secrets, cfn-nag, cdk-nag, cfn-lint, cfn-guard, actionlint, zizmor, npm-audit and the archive and Jupyter converters read. By default every file a .gitignore or .ignore in the scanned tree matches is left out of it, as git would leave it out. A nested ignore file applies to the directory it sits in, a later negation (!keep.log) puts a file back, and a directory the root .gitignore excludes is not entered at all, so the ignore files inside it are not read. ASH also leaves out files on its own: .git, CDK assets under cdk.out/asset.*, its bundled aws-cdk tree, and its own output directory when that is inside the source directory. A CloudFormation template (*.template.json) an ignore file matches is kept, unless it sits in a directory the root .gitignore excludes. bandit, semgrep, opengrep, checkov, grype and syft walk the source directory themselves, with their own ignore rules, so this setting does not change what they read: in a git checkout, semgrep and opengrep still skip the files git ignores. snyk-code gives the Snyk CLI a copy of the scan set rather than the source directory (see What ASH sends to Snyk).

    A link to a file is in the scan set only when its target, with every link on the way resolved, is inside the source directory. A link that leaves the tree (to an absolute path elsewhere, up through .., or through a link to a directory outside) is not scanned: a warning names it, as Not scanning 'vendor/config.py': link leaves the scanned tree, and names only the link, not where it points. Each one is also listed as an input not scanned, under ASH: in ash_aggregated_results.json under metadata.inputs_not_scanned (path and reason), in the console summary, and in the "Inputs not scanned" section of ash.summary.md and ash.summary.txt; in a workspace scan, in that project's inputs_not_scanned entry. A link to a file inside the tree stays in the scan set, and a source directory that is itself reached through a link is scanned as given. This applies to the readers of the scan set listed above.

    The scanners that walk the directory they scan themselves do not read the scan set. So ASH tells each of them to skip every link to a file whose target leaves that directory, or does not run it on that directory:

    • bandit reads a link to a file wherever it points (measured with bandit 1.9.4). ASH adds each such link to bandit's --exclude, as the link's own path.
    • checkov reads a link to a file wherever it points, whether the target is relative or absolute, and does not enter a link to a directory (measured with checkov 3.3.26). ASH passes one --skip-path for each such link, escaped and anchored so that it matches that path and no other: skipping a/main.tf does not skip a/main.tf.json. These values are ASH's own; the skip_path values in your config are passed as they are.
    • ferret-scan is given each such link in its --exclude, relative to the directory it scans. How ferret-scan treats links has not been measured.
    • grype and syft follow neither a link to a file nor a link to a directory whose target leaves the directory they scan (measured with grype 0.120.1 and syft 1.54.1). Each such link is still passed in their --exclude, as ./ and its path with the glob characters escaped, which leaves out that path and no other.
    • trivy (the trivy and trivy-repo scanners) skips every link, inside the tree or not (measured with trivy 0.75.0). Each such link is still passed in --skip-files, glob characters escaped, unless its path holds a comma, a double quote or a line break, which trivy's option cannot carry. Such a link is named in a debug log line (--log-level DEBUG).
    • gitleaks runs gitleaks dir without --follow-symlinks, which gitleaks reads as skipping every link.
    • semgrep and opengrep skip every link, inside the tree or not (measured with semgrep 1.180.0 and opengrep 1.30.2), and get no exclusion for one. Their --exclude cannot name one path: semgrep matches a pattern against paths below the git checkout's root when the scanned directory is inside one, and opengrep matches a top-level name at every depth. A link's name passed in --exclude could be one of the scanned directory's own names, and then semgrep left out every file in it.
    • snyk-code uploads the files it reads to Snyk, snyk code test has no option that leaves out one path, and how it treats links has not been measured by running it. So ASH does not run it on a directory holding such a link, or a link to a directory whose target is outside it (creds -> ~/.aws). Snyk's sources list files without walking into a link to a directory, but that has been read, not measured.

    ASH finds these links the way the tools walk: it does not read ignore files, so a link in a directory a .gitignore excludes is skipped too, and it does not enter a link to a directory. When bandit, checkov or ferret-scan cannot be given a link's path, ASH does not run that tool on that directory, rather than let it read the file the link points at; the same goes for snyk-code and any such link. The scanner's status is ERROR, and the error names the link, as Not running bandit on /src: 'a,b.py': link leaves the scanned tree, and bandit's --exclude cannot leave out that file alone, ... (bandit was not started). It carries no exit code, since the tool did not run. bandit cannot be given a path with a comma or one of *, ? and [, or a path that another file's path contains, because it also leaves out every path an entry is part of. ferret-scan cannot be given a path with a comma or any of *?[]{}\. checkov cannot be given any on Windows, where it joins the paths it walks with \. For the scanners that follow no such link, a path their option cannot carry is only left out of it, and on Windows none is passed.

    honor_ignore_files is a top-level key, and it defaults to true. To scan the files the repository's ignore files match as well, set it to false in a config file outside the scanned tree and every other git checkout, or for one scan:

    ash --source-dir . --no-honor-ignore-files
ash --source-dir . --config-overrides 'honor_ignore_files=false'

    ASH's own exclusions still apply then. --honor-ignore-files sets it back to true for one scan. Either form of the flag takes precedence over the config value, and in container mode the flag reaches the scan inside the container. In workspace mode it applies to every project.

    Whether the repository's ignore files hide its own files is the operator's decision, so a config file inside the scanned tree cannot set this key in either direction; see Settings a repository's config cannot choose. An MCP client cannot set it either: a client's config file is treated the same way, and /honor_ignore_files is in the default runtime_overrides.denied_paths.

    Every scan records the outcome in ash_aggregated_results.json, under metadata.ignore_file_exclusions:

    "ignore_file_exclusions": {
  "honored": true,
  "excluded_file_count": 7,
  "by_ignore_file": {
    ".gitignore": 3,
    ".ignore": 1,
    "vendor/.gitignore": 2,
    "sub/.ignore": 1,
    "sub/deep/.gitignore": 0
  },
  "output_dir_file_count": 0
}

    excluded_file_count is the number of files the ignore files removed, counted from the scan set itself: every file the walk found that is not in it, less the ones ASH leaves out on its own. by_ignore_file says which ignore file removed each one. Each ignore file is listed by its path relative to the source directory, with 0 when it removed nothing. A line that starts with # is a comment, as in git, and is not copied into ash-ignore-report.txt. The files under a directory the root .gitignore excludes count for the root .gitignore. A symlink (or junction) to a directory is never followed, so the files behind it are in no scan set and are not counted. With honor_ignore_files: false the record reads "honored": false with a count of 0.

    ASH's own output directory is left out whatever honor_ignore_files says. It is recognized as the same directory however its path is spelled (through a link in the source path, or as /src/.ash/ash_output and /out in container mode), not by its name; on a file system that reports no inode numbers, its absolute path decides instead. Files that are already in it when the scan set is built, this run's ash.log and ash.log.jsonl aside, are counted in output_dir_file_count, also when it sits under a directory the root .gitignore excludes, and the summaries say they were left out, and a warning names the directory. They are an earlier run's output, or repository files that sit where ASH writes; to scan repository files there, write ASH's output outside the scanned tree with --output-dir.

    When the output directory is inside the source directory, ASH also writes a .gitignore there holding * before any scanner starts, unless something is already at that name. A tool that reads the tree itself and honors .gitignore files then leaves ASH's output out too, and so does git. An existing .gitignore there is left as it is, nothing is written for an output directory outside the tree, and a link at that name stops the scan with exit code 3, as one at ash.log does. snyk-code does not rely on the file: snyk code test uploads what it reads, and that it honors a .gitignore is read from snyk's sources, not measured, so snyk-code refuses a source directory that holds ASH's output directory. Pass --output-dir with a directory outside the scanned tree to run snyk-code on the source.

    ash.summary.txt and ash.summary.md print the total in their scan metadata, for example Ignore files: the scanned repository's .gitignore and .ignore files excluded 7 files from ASH's scan set, or say that the ignore files were not honored. ash report --format text and --format markdown print the same line from the stored results. The MCP get_scan_summary tool returns the record under metadata.ignore_file_exclusions. In a workspace scan, each project's record is in workspace.projects[].ignore_file_exclusions, and the merged results and summaries carry the workspace total, with each ignore file keyed by its path relative to the workspace root. When the merged scans disagree (some projects, or some ash merge shards, honored the ignore files and some did not), the record also carries honored_scan_count and scan_count, honored is false, and the summaries say, for example, honored by 1 of 2 merged scans and not by the other 1 (honor_ignore_files: false); the ignore files that were applied excluded 7 files from ASH's scan sets. A project or shard that recorded no ignore-file record (it built no scan set, or an older ASH wrote its results) is not counted in scan_count. A record whose counts contradict each other or honored prints recorded inconsistently instead of either sentence. The log names every ignore file and its count at INFO level, and ash-ignore-report.txt in the output directory holds the rules that were applied.

    Global Settings

    The global_settings section controls general behavior:

    global_settings:
  # Minimum severity level to consider findings actionable
  # Options: ALL, LOW, MEDIUM, HIGH, CRITICAL
  severity_threshold: MEDIUM

  # Paths to ignore during scanning
  ignore_paths:
    - path: 'tests/test_data/'
      reason: 'Test data only'
    - path: '**/vendor/'
      reason: 'Vendored third-party code'
    - path: 'node_modules/'   # Also drops dependency-scanner findings located there
      reason: 'Third-party dependencies'
    - path: 'vendor/legacy-sdk/**'
      reason: 'Vendored copy, removed by the SDK upgrade'
      expiration: '2027-06-30'  # Optional expiration date (YYYY-MM-DD)

  # Findings to suppress based on rule ID, file path, and line numbers
  suppressions:
    - rule_id: 'RULE-123'  # Scanner-specific rule ID
      path: 'src/example.py'  # File path (supports glob patterns)
      line_start: 10  # Optional starting line number
      line_end: 15  # Optional ending line number
      reason: 'False positive due to test mock'  # Reason for suppression
      expiration: '2025-12-31'  # Optional expiration date (YYYY-MM-DD)

    An ignore path's path is a glob matched against a file's path below the source directory, anchored at both ends, with ** for any number of directories. One ending in / names a directory and ignores what is inside it, as <dir>/*/** does, never a file of that name: tests/test_data/ is what is inside the top-level tests/test_data directory, and **/vendor/ what is inside a vendor directory at any depth. So **/.*/ ignores the files in dot-directories such as .git/ and .cache/, and not dotfiles such as .env. An ignore path drops every finding below it, a dependency scanner's included, so **/node_modules/ hides the vulnerabilities npm-audit reports. A path naming a directory without the slash, such as tests/test_data, matches no file in it, and ash config lint warns about one. A suppression's path is read differently: one ending in / matches no file, and ASH warns after the scan about each such suppression that matched nothing, naming the <dir>/**/* that would. bandit and checkov also skip node_modules, .venv and venv directories on their own; ASH does not drop findings there, since the dependency scanners report theirs there (npm-audit at node_modules/<package>/package.json).

    An ignore path is a suppression. ASH does not convert a file under one or include it in the file lists it hands scanners, and leaves a finding any scanner reports there out of the results. The scanners that walk the directory themselves are also told to leave out the files an ignore path matches, matched the same way: each ignored file, or once for a directory whose every file is ignored.

    • bandit: in its --exclude;
    • grype and syft: --exclude ./<path>, and ./<dir>/** for a directory;
    • trivy and trivy-repo: --skip-files and --skip-dirs;
    • checkov: one --skip-path each, anchored so it matches that path alone;
    • semgrep and opengrep: --exclude=<name>, only for a name that nothing else below the scanned directory, and nothing in that directory's own path, has.

    cfn-lint and cfn-guard pick their templates from the file lists ASH hands scanners, so an ignored template is not linted, as cfn-nag does not read it.

    A path a tool's option cannot carry (one with a comma for bandit and trivy, or a name that is not unique for semgrep and opengrep) is still read by that tool, and ASH drops what it finds there. gitleaks has no option that leaves out a path, so it still reads the files an ignore path matches, and ASH drops what it finds there. snyk-code has no such option either and uploads the files it reads, so it refuses a directory holding a file an ignore path matches, whether the source directory or ASH's directory of converted files, wherever that is. Each file is matched as ASH matches the location snyk reports for a finding in it, its path below the directory snyk tests, so a file is refused exactly when the operator's ignore paths would have ASH drop its findings: a converted file by its path below the directory of converted files, such as archive/src__bundle__zip/vendor/m.js. An ignore path naming a source archive or notebook exactly keeps it from being converted at all. It is ERROR, snyk code test is not started, and the error names the first such file and the pattern that matched it, gives the number of files and the patterns, and suggests narrowing ignore_paths or --exclude-scanners snyk-code. On Windows the other tools are given none of these. --ignore-suppressions lifts ignore paths along with suppressions: every scanner reads those files and their findings are reported. See Temporarily Disabling Suppressions.

    An ignore path also names the members of an archive ASH extracts (.zip, .tar, .gz), in the scanned tree's own terms: by the archive's path and then the member's, as if the archive were a directory (lib/bundle.zip/vendor/m.js, lib/bundle.zip/vendor/**). Such a member is not extracted, so no scanner reads it. A pattern that matches at any depth, such as **/vendor/**, also matches through the archive's name, so it leaves out the members under a vendor/ in the archive too. A path in the tree names no member: vendor/**, or an ignore path for the file lib/vendor/m.js, leaves out the tree's files and keeps lib/bundle.zip's vendor/m.js in the scan. A single * also matches / in ASH's patterns, so *.js, lib/*.js, lib/**/*.js and */vendor/* reach lib/bundle.zip's members as well. An ignore path matching the archive itself (lib/bundle.zip) leaves out the whole archive.

    An expiration works the same way on an ignore path and on a suppression: a quoted YYYY-MM-DD date, read on the local clock of the host running the scan (UTC in container mode, where the ASH image sets TZ=UTC). On that date the entry stops applying, so the ignored files are scanned again or the suppressed findings count again. For the 30 days before it each scan logs a warning naming the entry, and after it one warning at the start of each scan lists the expired entries. A date in another format refuses the configuration (exit code 3). See Expiring Suppressions.

    Omitting line_end does not suppress only line_start. A suppression with line_start and no line_end matches every finding from that line to the end of the file, including findings introduced later. To suppress a single line, set line_end to the same value as line_start. To follow a function or class when lines move, use symbol instead; see Suppressing by symbol.

        - rule_id: 'RULE-123'
      path: 'src/example.py'
      line_start: 10
      line_end: 10  # Without this, lines 10 onwards are all suppressed
      reason: 'False positive due to test mock'
    - rule_id: 'RULE-456'
      path: 'src/*.js'  # Glob pattern matching all JS files in src/
      reason: 'Known issue, planned for fix in v2.0'
    - rule_id: 'B602'
      path: 'src/deploy.py'
      symbol: 'Deployer.run_hook'  # Only findings inside this method; needs the [symbols] extra
      reason: 'Hook command comes from the signed manifest'

  # Whether to fail with non-zero exit code if actionable findings are found
  fail_on_findings: true

    An unrecognized option refuses the configuration

    An option a plugin does not declare stops the run with exit code 3 (invalid configuration). The error names the plugin by where the option sits and names the key, with a suggestion when a declared option is close: severity_level: HIGH on bandit fails with scanners.bandit.options: Unknown key 'severity_level' (did you mean 'severity_threshold'?). An undeclared key is never read, so the refusal is what keeps a misspelled setting from silently having no effect.

    The same goes for a key at the section level, beside enabled, other than enabled, options, name and a reporter's extension. An option written there is not read, so the error says where it goes: severity_threshold: HIGH directly under scanners.bandit fails with scanners.bandit.severity_threshold is not a section-level key; move severity_threshold under options. Any other key is named as unknown. tool_version, install_timeout and a scanner's extension beside enabled are named as internal-only fields instead, because moving a leaked tool_version under options would pin the tool's version. A scan and ash config validate print the same message for them; ash config lint reports each field as an issue of its own, at its path. Where the plugin also declares an option of that name (bandit, checkov, semgrep, jupyter, ferret-scan), the message adds if you meant a version constraint, put it under options. ash config lint --fix removes these fields, except a tool_version or install_timeout that is neither null nor equal to the plugin option's default (for a plugin loaded from ash_plugin_modules, which lint does not load, anything but null): that can be a pin you meant, so it is left for you to move under options or remove. A field an extends base sets is reported but not removed, since --fix edits only the file it lints.

    scanners:
  bandit:
    enabled: true
    options:
      severity_threshold: HIGH   # not beside enabled

    For a built-in plugin the options are checked when the configuration loads. For a plugin loaded from ash_plugin_modules, they are checked once the plugins are loaded, before anything is converted or scanned; a value the plugin's own options model rejects fails there too, with that plugin's message. Options for a plugin that the run does not load cannot be checked, and are left as they are.

    The same applies to the entries of suppressions and ignore_paths, global or in a scanner option of the same kind (bandit excluded_paths, checkov skip_path, syft exclude): ruleId: B101 fails with Unknown key 'ruleId' (did you mean 'rule_id'?). The key is refused rather than dropped because a suppression with no rule suppresses every rule in its path. In a workspace policy file the same key refuses the policy, and ash scan exits 4, the code for a workspace definition or policy error.

    ash config validate and ash config lint check the options of built-in plugins only. They do not import the modules listed in ash_plugin_modules, so they cannot know what those plugins declare, and a configuration they pass can still be refused by a scan for an option of such a plugin. Both name those sections: validate in a note after its verdict lines, lint in one INFO issue, category plugin-options-unchecked. Run a scan to check their options.

    A results file written by another ASH version can hold such a key. It still loads for ash report, ash merge and the other readers of results: the key is kept, a warning names it, and an entry that has one is never applied.

    Bounding how long a scanner may run

    Every scanner accepts scan_timeout, the number of seconds its tool invocation may run before it is killed. The default is 1800 (30 minutes). Set it to null to leave a scanner unbounded:

    scanners:
  semgrep:
    options:
      scan_timeout: 3600  # An hour for a large repository
  syft:
    options:
      scan_timeout: null  # No limit

    A scanner killed by its timeout produces no results file, so the scan fails with an error naming the scanner and the limit (<scanner> timed out after '1800' s) rather than silently reporting zero findings for it. Whatever the tool wrote before it was killed is kept in scanners/<name>/<target>/<Scanner>.stderr.log under the output directory. While a scanner runs, ASH logs <scanner> still running on <target> (<N>s elapsed) at INFO once a minute, so a hung scanner is named in a CI log without any extra flag. scan_timeout bounds the scan itself; install_timeout separately bounds tool installation and defaults to 300.

    Custom Plugin Modules

    The ash_plugin_modules section allows you to specify custom Python modules containing ASH plugins:

    ash_plugin_modules:
  - my_custom_ash_plugins
  - another_ash_plugins

    Each entry must be a dotted path of Python identifiers inside ASH's plugin namespace: under automated_security_helper. or ash_plugins, or a top-level package named ash_plugins or ending in _ash_plugins (my_ash_plugins, but not myash_plugins). ASH's plugin root automated_security_helper.plugin_modules holds every plugin package ASH ships and names none of them, so name the package below it (for example automated_security_helper.plugin_modules.ash_trivy_plugins). A namespace package (a directory with no __init__.py, which can gather packages from several distributions) declares no plugins either, so name the packages it holds. One entry may name several modules separated by commas, and spaces around each name are ignored, whether the entry comes from a config file, --config-overrides, --ash-plugin-modules or ASH_PLUGIN_MODULES. Any other entry, such as another_plugin_module, the plugin root, a namespace package, or a name with a space inside it, refuses the scan with exit code 3 (invalid configuration) before any module is imported, from any of those sources. The same name refuses ash plugin list, ash dependencies install, ash report and ash merge with exit code 3. A module that is named correctly but does not import, because it is not installed or its import raises an error, refuses a scan with exit code 3 too, before any scanner runs, and refuses ash plugin list, ash dependencies install and ash report the same way; the message names the module and the error. ash config validate and the MCP validate_config tool report a name a scan refuses as a validation error; they import nothing, so they do not check whether an accepted name imports. When the list comes from a config file inside the scanned tree, only installed modules are imported; see Settings a repository's config cannot choose.

    A scan uses ASH's built-in plugins (those defined in automated_security_helper.plugin_modules.ash_builtin) plus the converters, scanners, reporters and event handlers of the modules its own ash_plugin_modules (from its config and --ash-plugin-modules) names. A module's plugins are those it defines itself, imports into its namespace, or lists in its ASH_* declarations; naming a package does not select a plugin that only one of its subpackages defines, so name that subpackage. This holds when one process runs several scans, as the MCP server does: a module that an earlier scan named, or that the MCP list_scanners tool loaded to describe the community scanners, takes no part in a scan that does not name it, and a module that only a later scan names takes part in that scan. An event handler defined outside ASH's plugin namespace, such as one a program that calls run_ash_scan subscribes with ash_plugin_manager.subscribe, is notified in every scan that program runs.

    Settings a repository's config cannot choose

    ASH reads its configuration from the repository it scans unless --config names a file elsewhere. A few settings decide what ASH installs, imports or hands a scanner as its own configuration, so they are limited when someone other than the operator could have written them. Two terms are used below:

    • Repository-written: inside any git checkout, or inside the source directory when that is outside every checkout. A checkout is something other people can push to, so this includes a checkout of your own, such as an ops or dotfiles repository. Under the MCP server, a file any MCP client delivered counts too: everything under the MCP workspace root ($ASH_MCP_WORKSPACE_ROOT, by default ~/.cache/ash-mcp/) except the profile files the server writes in each session's config/ directory: ash.yaml, the profile select_profile binds, and a workspace tool's per-call profile, one file per profile named call-profile- followed by 16 lowercase hex digits and .yaml (or call-profile.yaml). Only a file directly in config/ with one of those names is the server's. Any other file there is the client's, and neither config/ nor client-config/ may be a scan target or an output directory. A profile a client patched with select_profile is written to the session's client-config/ directory instead, so it counts as the client's.
    • The scanned tree: the source directory, or the outermost git checkout holding it.

    A file is judged by the path as written, relative to the source directory, by the file it resolves to, and by every symlink resolving it follows, so a symlink the scanned repository planted counts where it sits and where it points, and so does a path of your own that leads through one.

    A config is limited when any file it was built from is repository-written: a discovered .ash/.ash.yaml, a --config path, an extends base, or the file ASH_CONFIG names. Under the MCP server, a config file a client delivered (an upload or a file in a delivered tree, named as config_path) is limited the same way, wherever it is. Pass ash_plugin_modules and the sandbox settings with --ash-plugin-modules or --config-overrides instead, or keep the config file outside every checkout.

    A file that one of the path settings below names is judged by who named it:

    • Named by the operator, with --config-overrides, in a config file that is not repository-written (outside every git checkout and the source directory), or through an environment variable such as TRIVY_IGNOREFILE: it is passed to the tool unless it is inside the scanned tree or an MCP client delivered it. A tool config or ignore file kept in an ops repository works.
    • Named by a repository-written config or one an MCP client delivered, or found by name in the source directory: it is passed only when the file is not repository-written, so the repository cannot point a tool at a file in someone's checkout. A config file kept in an ops checkout is repository-written too, as it is for the other settings here, so the paths it names follow this rule, a tool config in that same checkout included. The warning says how to keep the setting: move the config file outside every git checkout, or pass the setting with --config-overrides.

    When the operator's config file extends a repository-written one, only the paths the operator's file writes itself count as the operator's. An MCP client's config_overrides, and a session profile its select_profile patch_ops or override_yaml changed, count as the client's.

    The trivy, trivy-repo, cfn-lint, cfn-guard, actionlint, gitleaks and zizmor settings in the table are judged by the config as a whole. A value is the operator's when it comes from --config-overrides or from a config that is not limited (above), and only then: in a limited config, even a value the operator's own file writes is not, when that file extends a repository-written base. Set it with --config-overrides.

    Setting Limit
    scanners.<name>.options.tool_version, converters.<name>.options.tool_version Taken from the defaults, --config-overrides or a config file outside the tree, for every scanner and converter, including those a plugin module adds. It chooses which release of the tool ASH installs and which one already on PATH it accepts. A value equal to the operator's applies; any other is ignored with a warning, and the operator's value or the tool's default constraint applies. From every source, including --config-overrides, it must also be a PEP 440 version specifier set such as >=1.2,<2 or ==1.4.1; any other value is replaced by the default constraint.
    scanners.opengrep.options.version Must be a release tag such as v1.15.1, from every source. Any other value is replaced by the pinned version.
    content_db_staleness, content_db_staleness_overrides, content_db_staleness_offline_image_default warn, an overrides entry with policy: warn, and an offline image default of true where the operator's is false, are taken from the defaults, --allow-stale-content-db, --config-overrides or a config file outside the tree. From the tree's config such a value is ignored with a warning unless it equals the operator's, and the scan fails on a stale database as by default. fail, an entry with policy: fail, and an offline image default of false apply from every config.     ash_plugin_modules From a repository-written config, an entry is imported only if it names an installed module that Python finds in a location that is not repository-written. A virtualenv inside a git checkout counts as inside it, so a module installed there is skipped too; the warning gives the module's location and the checkout. So are automated_security_helper.plugin_modules.ash_aws_plugins and automated_security_helper.plugin_modules.ash_snyk_plugins, and any module inside either: the AWS reporters send findings to AWS with the operator's credentials, and the Snyk Code scanner sends the scanned source to Snyk with the operator's Snyk token, so only --ash-plugin-modules (or ASH_PLUGIN_MODULES), --config-overrides or a config file that is not repository-written can add them. The same holds for their classes when another package a repository-written config loads lists or imports them: a scanner or reporter defined in either package is selected only when one of those operator sources loads that package, a module inside it, or the package that lists the class, and each one dropped is named in a warning.     Configs an MCP client delivered

    ASH's configuration can come from three places, and how far it is trusted depends on which:

    • The operator: ASH's defaults, a config file outside the scanned tree (named by --config or ASH_CONFIG), --config-overrides, --ash-plugin-modules, and, under the MCP server, the profiles the server registers. Everything applies. An operator file in a git checkout other than the scanned one grants nothing, as a config in the scanned tree does, but what it sets that only restricts still holds: a lowered archive extraction limit, metrics: off for semgrep and opengrep, disable_telemetry: true for trivy, and a sandbox.network_scanners list as a limit on which scanners get a network. If an MCP client delivered the file, none of it holds. Such a file also loses the options only the operator sets, the ones in the table above that name --config-overrides or a config file outside the tree: they come from the defaults, --config-overrides, or a file outside every git checkout and the scanned directory, and one warning names each option and the file. The same holds for the reporters that send findings off the host (aws-security-hub, bedrock-summary-reporter, cloudwatch-logs, s3): a section such a file writes for one of them is not used, whether the file is the --config, the file ASH_CONFIG names or the operator's trusted config for a workspace, so the reporter runs only when the defaults or --config-overrides turn it on, and one warning names the section and the file. To keep a setting, move the file outside every git checkout (a config kept in an ops or dotfiles repository counts as inside one), or pass the setting with --config-overrides.
    • The repository being scanned: a config file inside the scanned tree, or a file a symlink inside the tree reaches, wherever that file is. The table above applies.

    • An MCP client: a file the client delivered, such as an upload named as config_path, a delivered tree's own .ash/.ash.yaml, or a project config in a delivered workspace. So is any other config path a client names, unless it is in a directory ASH_MCP_ALLOWED_CONFIG_ROOTS names or is a profile file the server writes in the session's own config/ directory: a config in another checkout the server may scan is that checkout's, not the operator's. A path is judged where it sits, at each symlink on the way, and by the file it reaches, so a link a client delivered is the client's wherever it points, and so is a file reached through a linked directory such as .ash. A file under the MCP workspace root is a client's whoever names it: a --config or ASH_CONFIG naming one, on the CLI as well, gets the limits of a config inside the scanned tree, and the server's runtime-override policy is never read from it (the built-in defaults apply instead). A profile after the client's select_profile patch_ops or override_yaml is the client's too, held to the registered profile as its trusted base, and so are the MCP workspace tools' config_overrides, even for keys the runtime-override allowlist lets the client change. The table above applies, and so does the session's runtime-override policy, global_settings.mcp.runtime_overrides:

    • The file may not change a field that denied_paths or denied_value_patterns denies. Entries match either - or _, every spelling of a plugin's section, and globs such as /scanners/trivy-*/options/ignore_file. A value equal to the server's is accepted, so a file ash config init wrote scans. A file that changes a denied field is refused with error_type: config_field_denied, naming each field. When the policy cannot be established, a scan that reads such a file is refused with error_type: config_policy_unreadable.

    • It may restrict the server's sandbox and ash_plugin_modules settings but not ask for more than they give: a network_scanners entry for a scanner the server's config gives no network, an extra_read_paths entry the server's config does not grant, a mode other than the server's when the server sets one, or a module the server's config does not load that is inside the scanned tree or sends findings off the host. A file that does is refused the same way, naming the setting; an equal or tighter value scans.
    • What chooses a scanner's own config, which version of a tool ASH installs, or where findings go is in the default denied_paths too, so a file that sets one is refused rather than scanned without it: each scanner's own config file (config_file for actionlint, bandit, cfn-lint, checkov, ferret-scan, gitleaks, grype, syft, trivy, trivy-repo and zizmor, and trivy's and trivy-repo's secret_config_file), trivy-repo's module_dir, cfn-guard's rules_paths, the programs actionlint runs (shellcheck, pyflakes), zizmor's online_audits (which lets the GitHub token reach zizmor), snyk-code's honor_tree_exclusions, the honor_inline_ignores of cfn-lint, gitleaks and zizmor (which honor the ignore comments in the scanned files), every scanner's and the jupyter converter's tool_version, opengrep's version and sha256, opengrep's and semgrep's metrics (their config is in the table below), the AWS reporters' destinations and credentials listed in the table above, whether aws-security-hub, s3, cloudwatch-logs and bedrock-summary-reporter run (enabled; false is not refused, here or in a client's runtime overrides, but it takes no effect: the server's enabled applies, as in the enabled row above, and a warning names the client's value. A reporter that writes only local files is not covered), every other aws-security-hub, s3 and bedrock-summary-reporter setting (each section is a whole-section entry, as cloudwatch-logs is), and the GitLab SAST reporter's exclude_suppressed, which would leave the findings a client's suppressions are marked on out of that report.     Validating Configuration

    To check that a scan accepts your configuration:

    ash config validate

    ash config validate loads the file the way a scan does, with its extends chain, ${VAR} and !ENV references and the AshConfig model the JSON schema is generated from. When a scan would refuse the configuration, it lists every field the model refuses and exits 3, the exit code a scan gives for an invalid configuration. Problems a scan tolerates, such as an unknown top-level key, an internal-only field a section declares (name) or the build section, are printed as warnings and leave the exit code at 0, in ash config lint too. A file that does not parse also exits 3, and a scan refuses it with exit 3 too. Pass the --config-overrides a scan will get to check the configuration with them applied, and --source-dir when the scan will not run from the current directory. ash config lint runs the same checks, adds suppression checks, and can fix some issues; see the CLI reference for both.

    Viewing Current Configuration

    To view the current configuration:

    ash config get

    Updating Configuration

    To update configuration values:

    ash config update --set 'scanners.bandit.enabled=true'
ash config update --set 'global_settings.severity_threshold=LOW'

    --set takes the same syntax as --config-overrides, and is applied by the same code. If any --set cannot be parsed, or leaves a configuration a scan would refuse, nothing is written and the command exits 3. The file is rewritten with every setting, defaults included, except the internal-only fields (build, and name or extension under a scanner, reporter or converter) and an unchanged mcp-resource-management section, and comments other than the schema line are not kept. Top-level keys ASH does not know, such as a JSON $schema, are kept as written. A .json file is written back as JSON. ash config update and ash config wizard refuse to rewrite a file that reads values from the environment (!ENV, or ${VAR:default}), because the rewrite would store the values the references resolve to; edit such a file by hand. MCP profiles are saved with the same writer. ash config wizard also refuses a file it cannot load (exit 3) rather than starting from the defaults and overwriting it.

    Configuration Overrides

    You can override configuration values at runtime using the --config-overrides option:

    # Enable a specific scanner
ash --config-overrides 'scanners.bandit.enabled=true'

# Change severity threshold
ash --config-overrides 'global_settings.severity_threshold=LOW'

# Append to a list
ash --config-overrides 'ash_plugin_modules+=["my_ash_plugins"]'

# Add a complex value
ash --config-overrides 'global_settings.ignore_paths+=[{"path": "build/", "reason": "Generated files"}]'

    Relative paths in the operator's settings

    A relative path in one of the operator's settings is taken from where it was set, not from the source directory being scanned:

    • in a config file outside the tree (--config, ASH_CONFIG, a workspace's --config, an MCP profile), from that file's directory; in an extends base, from the base's directory; and in a patch operation, from the directory of the file that holds it;
    • in --config-overrides, in a CLI flag, and in TRIVY_IGNOREFILE, TRIVY_SECRET_CONFIG or TRIVY_CONFIG, from the working directory ASH runs in.

    This covers config_file of actionlint, bandit, cfn-lint, checkov, ferret-scan, gitleaks, grype, syft, trivy, trivy-repo and zizmor, gitleaks' baseline_path, each entry of cfn-guard's rules_paths, detect-secrets' baseline_file and the file:// entries of its scan_settings, trivy's and trivy-repo's ignore_file and secret_config_file, trivy-repo's module_dir, opengrep's and semgrep's config when a file or directory is there (otherwise it is a registry entry such as p/ci), and sandbox.extra_read_paths. It does not cover actionlint's shellcheck and pyflakes, which name a program: a bare name there is looked up on PATH, and a relative path is taken from the source directory. A path that starts with ~, or is absolute, is used as written. In TRIVY_IGNOREFILE, TRIVY_SECRET_CONFIG and TRIVY_CONFIG, any other value is taken from the working directory exactly as written, a $ or :// in it included, and a .. after a symbolic link goes up from where the link points. A config file inside the scanned tree does not set these options (see Settings a repository's config cannot choose). To name a file in the scanned repository, give its absolute path, or a path relative to where you run ASH with --config-overrides.

    Extending another configuration

    A config can build on one or more base configs with extends, and adjust the result with RFC 6902 JSON-Patch operations under patch:

    # ASH config file (.ashrc.yaml in a new project)
extends: shared/ash-base.yaml        # or a list: [org.yaml, team.yaml]
project_name: my-service
global_settings:
  severity_threshold: HIGH
patch:
  - op: add
    path: /global_settings/suppressions/-
    value:
      rule_id: B101
      path: "tests/**"
      reason: "assert is expected in tests"

    The same keys work in [tool.ash] (extends = "ash-base.yaml", patch = [{op = "add", path = "/fail_on_findings", value = false}]) and in an ashrc file. A base can be YAML, JSON, TOML, or a pyproject.toml, whose [tool.ash] table is used.

    How a config is resolved:

    1. Each base is resolved the same way, so bases can extend other bases.
    2. The bases are merged in the order listed, a later base winning over an earlier one.
    3. The file's own settings are merged over the bases. The file always wins.
    4. The file's patch operations run, in order, on the result.
    5. --config-overrides apply last, on top of everything above.

    Merge rules:

    • Mappings merge key by key, at every level. A base's scanners.bandit.options and a child's scanners.bandit.enabled both survive.
    • Lists, scalars and null replace. A child that sets global_settings.suppressions replaces the base's list. To keep the base's entries and add more, use patch with op: add and a path ending in /-.
    • To delete something a base set, use patch with op: remove.
    • A setting is merged as ASH reads it. Where ASH reads one setting under two spellings (cdk-nag and cdk_nag), both are the one setting: the child's value wins over the base's whichever spelling either file uses, and the result is kept under one spelling. A spelling ASH does not read (global-settings for global_settings) in a base is left alone, so it cannot keep a child's value from applying; one in a child still reaches the base's spelling of the setting, unless the child also uses a spelling ASH reads, which wins. Two spellings of a plugin's section that ASH reads for the same plugin (BedrockSummary and bedrock-summary-reporter) are one section, under the child's spelling. In patch paths, a key spelled with - and the same key spelled with _ are one key.
    • patch accepts add, remove, replace and test. move and copy are refused. A failing operation, including a failing test, fails the load.

    Where a base may live:

    • A relative path is relative to the file that names it. An absolute path is also accepted.
    • Every base must be inside the scan's source directory (or, for a --config file kept outside it, inside that file's own directory, or the parent of .ash/ for a file in .ash/). .. is fine while it stays inside. A path, or a symlink, that resolves outside is an error. In workspace mode each project is scanned with its own directory as the source directory, so a project's bases must be inside that project.
    • URLs are refused. ASH never downloads a base config; copy the file into the repository instead.

    Errors stop the scan rather than falling back to the default configuration: a missing or unreadable base, a cycle (the error prints the chain, for example .ash.yaml -> b.yaml -> c.yaml -> b.yaml), a chain more than 10 levels deep, or more than 50 files read in total. ${VAR} references in every file of the chain are resolved under the same allowlist as a single file.

    ash config validate and ash config lint follow the chain, report extends errors, and print the files the config was built from, lowest precedence first. ash config update, ash config wizard and the ash inspect suppression dialog refuse to rewrite a file in a way that would copy its bases into it or drop their suppressions.

    Scanner-Specific Configuration

    Each scanner has its own configuration options. Here are some examples:

    Bandit

    scanners:
  bandit:
    enabled: true
    options:
      confidence_level: high      # all | low | medium | high -- lowercase only
      severity_threshold: MEDIUM  # ALL | LOW | MEDIUM | HIGH | CRITICAL -- uppercase only
      ignore_nosec: false         # true scans lines carrying a '# nosec' comment anyway
      excluded_paths: []          # Paths to exclude, each with a reason
      config_file: null           # The operator's bandit config file; see below
      scan_timeout: 1800          # Seconds before the bandit invocation is killed
      # Bandit is installed via UV tool management with the constraint
      # '>=1.7.0,<2.0.0' for SARIF support.

    Selecting individual bandit tests is done in a bandit configuration file rather than through ASH options. ASH does not look for one by name in the scanned tree. Name it with config_file, set with --config-overrides or in a config file outside the tree; a config file inside the tree does not set it (see Settings a repository's config cannot choose). A relative path is taken from where it was set, as for the operator's other paths (Relative paths in the operator's settings). A file named exactly .bandit is passed with bandit --ini, and any other file with bandit --configfile. Unless config_file names a .bandit file that exists, ASH passes bandit an empty config file with bandit --ini, so bandit does not read a .bandit file from the tree either. A path that is not a file is logged as a warning and ignored. For the file's format, refer to the Bandit documentation.

    scanners:
  detect-secrets:
    enabled: true
    options:
      baseline_file: null   # Explicit .secrets.baseline path, relative to the config file that sets it
      scan_timeout: 1800    # Seconds before the detect-secrets invocation is killed

    Which plugins and filters run, and which findings are already accepted, live in the detect-secrets baseline rather than in ASH options. Point baseline_file at one, or rely on the discovery described below. The scan_settings option takes the same structure as a baseline's own settings block if you would rather inline it.

    If you have been using detect-secrets separately and have an existing baseline file you would like to use with ASH, ASH can use it automatically. It looks for .ash/.secrets.baseline, then .secrets.baseline, in the source directory (--source-dir), wherever ASH is run from, and takes a relative baseline_file from the source directory too. A baseline in the directory ASH runs from does not apply to a scan of another directory. For more details on baseline files, refer to the detect-secrets documentation.

    Secret verification

    detect-secrets can verify a candidate secret by sending it to the service that issued it, and drop the candidates the service rejects. The filter that does this is detect_secrets.filters.common.is_ignored_due_to_verification_policies, and detect-secrets scan writes it into every baseline it generates. For an AWS access key the request goes to sts.amazonaws.com, signed with the key pair found in the scanned file, so verification makes the host running ASH contact the issuer with credentials taken from the scanned tree. ASH therefore verifies only when the operator asks for it, and never in offline mode:

    • The filter counts when the operator's own configuration names it: a config file outside the scanned directory and every git checkout (--config or ASH_CONFIG), --config-overrides, or for the MCP server the profile the session is bound to. An MCP client's runtime overrides cannot set these detect-secrets settings: they are always in runtime_overrides.denied_paths, whatever allowed_paths says. A profile that sets its own denied_paths adds to them and cannot remove them, as for the scanner sandbox, ash_plugin_modules and the archive extraction limits. It can be in scan_settings.filters_used, or in a baseline_file the operator names that is outside the scanned tree and outside the git checkout holding it, including through --config-overrides beside a repository's own config. A baseline in another checkout counts: scanning repo/service with a baseline from a separate shared-baselines checkout verifies, while one in repo/ops does not.
    • When scan_settings sets plugins_used or version, it replaces the baseline's plugins and filters. Otherwise the baseline's are used, and a verification filter the operator's scan_settings.filters_used names is kept beside them.
    • A .secrets.baseline inside the scanned tree or its checkout, a config file the scanned repository holds (.ash/.ash.yaml and the other discovered names, including a workspace project's own config), and a config an MCP client supplied cannot turn verification on, whatever baseline they name. ASH removes the filter, keeps the rest of the settings, and logs a warning that names the source.
    • Under --offline (or ASH_OFFLINE) nothing turns it on.

    To verify, name the filter with its min_level in your own config. detect-secrets reads min_level for this filter, and without it the scan fails:

    scanners:
  detect-secrets:
    options:
      scan_settings:
        filters_used:
          - path: detect_secrets.filters.common.is_ignored_due_to_verification_policies
            min_level: 2

    The same sources decide which plugin and filter files detect-secrets may import. A plugins_used or filters_used entry named by file:// path is a Python file the detect-secrets worker loads, so only the operator's own configuration, or a baseline outside the scanned tree and its checkout that the operator names, may name one. The file itself must also be outside the scanned tree and every git checkout. A file:// entry in a repository's config or .secrets.baseline, or in a baseline such a config names, is removed with a warning, wherever the file is; the built-in detectors it lists by name still run.

    When verification is off, candidates the filter would have dropped are reported, so a repository whose own baseline used to verify can show more findings. The detect-secrets worker also refuses every HTTP request in that case, so a filter or plugin that verifies under another name sends nothing either. Under --sandbox, verification also needs sandbox.network_scanners to name detect-secrets; see Scanner sandbox.

    UV Tool Management

    ASH v3 uses UV's tool isolation system to automatically manage scanner dependencies. This provides several benefits:

    • Automatic Installation: Tools like Bandit, Checkov, and Semgrep are automatically installed when needed
    • Version Constraints: ASH ensures compatible tool versions with sensible defaults:
    • Bandit: >=1.7.0 (enhanced SARIF support and security fixes)
    • Checkov: >=3.2.0,<4.0.0 (improved stability, avoiding potential breaking changes)
    • Semgrep: >=1.125.0 (comprehensive rule support and performance improvements)
    • Isolation: Tools run in isolated environments without affecting your project dependencies
    • Retry Logic: Automatic retry with exponential backoff for network issues
    • Comprehensive Logging: Detailed installation and execution logging for troubleshooting
    • Fallback Support: If UV tool installation fails, ASH falls back to system-installed tools when available

    UV Tool Configuration Options

    Each UV-managed scanner supports these configuration options:

    scanners:
  checkov:  # or bandit, semgrep
    enabled: true
    options:
      tool_version: ">=3.2.0,<4.0.0"  # Override default version constraint
      install_timeout: 300             # Installation timeout in seconds (default: 300)

    Environment Variables

    Control UV tool behavior globally:

    # Disable automatic tool installation (use pre-installed tools)
export ASH_OFFLINE=true

# Custom UV executable path (if needed)
export UV_EXECUTABLE=/custom/path/to/uv

    Troubleshooting UV Tool Issues

    If you encounter UV tool installation issues:

    1. Check UV availability: uv --version
    2. Enable verbose logging: ash --verbose for detailed installation logs
    3. Use offline mode: ASH_OFFLINE=true to skip installations
    4. Pre-install tools manually: 
      uv tool install bandit>=1.7.0,<2.0.0
uv tool install checkov>=3.2.0,<4.0.0
uv tool install semgrep>=1.125.0,<2.0.0
    5. Increase timeout for slow networks: 
      scanners:
  checkov:
    options:
      install_timeout: 600  # 10 minutes

    For more detailed information about UV tool management, see the UV Tool Management Developer Guide. - Flexible Version Management: Scanners can optionally specify version constraints, with sensible defaults provided

    UV Tool Behavior

    • Bandit: Automatically installed via uv tool install bandit>=1.7.0,<2.0.0 (default version constraint)
    • Checkov: Automatically installed via uv tool install checkov>=3.2.0,<4.0.0 (default version constraint) with fallback to uv tool run
    • Semgrep: Automatically installed via uv tool install semgrep>=1.125.0,<2.0.0 (default version constraint) with fallback to uv tool run

    Version Constraint Configuration

    Each UV-managed scanner can specify version constraints in two ways:

    1. Default Constraints: Built-in version constraints ensure compatibility and stability
    2. Custom Constraints: Override defaults via configuration options (where supported)

    For scanners that support custom version constraints (like Semgrep and Checkov), you can specify them in a config file outside the scanned tree, or with --config-overrides. A repository's own config does not choose them; see Settings a repository's config cannot choose.

    scanners:
  semgrep:
    options:
      tool_version: ">=1.130.0,<2.0.0"  # Custom version constraint
  checkov:
    options:
      tool_version: ">=3.3.0"  # Custom version constraint

    Troubleshooting UV Tool Issues

    If you encounter issues with UV tool management:

    1. Check UV Installation: Ensure UV is installed and available in your PATH
    2. Network Connectivity: UV tool installation requires internet access
    3. Offline Mode: Use ASH_OFFLINE=true to skip tool downloads and rely on pre-installed tools
    4. Manual Installation: You can pre-install tools manually if needed: 
      uv tool install bandit>=1.7.0,<2.0.0

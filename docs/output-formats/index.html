    Output formats

    ASH produces scan results in multiple formats. Every scan writes an internal aggregated-results JSON file (ash_aggregated_results.json), and reporters transform that data into the formats listed below. You can enable any combination of reporters in your configuration or on the command line.

    The reports land in reports/ under the output directory (.ash/ash_output by default), beside ash_aggregated_results.json. The output directory also holds scanners/, each tool's raw output as the tool wrote it, and converted/, the converted copies of scanned files such as notebooks and archive contents. Those two are not masked: a secret a scanner found is in them in full. When you keep scan output as a CI artifact, keep reports/ and ash_aggregated_results.json only, as the examples in Running ASH in CI do. A workspace scan repeats the layout per project under projects/<key>/, so keep projects/*/reports and projects/*/ash_aggregated_results.json too, and not the projects' scanners/ or converted/.

    Every report, ash inspect findings, the summary counts, and the exit code grade a finding the same way: by the severity the scanner gives it (properties.issue_severity in SARIF) when it gives one, otherwise by its SARIF level, where error is CRITICAL, warning is MEDIUM, note is LOW, and none is INFO. A finding that states no level takes the level its rule declares as default (defaultConfiguration.level), or none when its kind is not fail, and otherwise SARIF's own default, warning (MEDIUM); a level ASH does not recognise is read as warning too. ash.sarif writes every finding's level, so a tool reading the file sees the level ASH graded. Formats with their own severity scale carry the same grade in that scale: GitLab SAST as Critical through Info, OCSF as severity_id 5 (Critical) through 1 (Informational), and the GitHub GHAS report, for a rule whose scanner gives no security-severity, as 9.5, 8.0, 6.0, 3.0, or 1.0.

    Each scan's results carry a metadata.report_id that no other scan shares: ASH-, the scan's start as a UTC date and time, and 12 random hexadecimal digits, for example ASH-20261011153012-3f9c0e2b7d1a. Reports rendered again from saved results, with ash report or --use-existing, keep the id. ash merge gives the merged report one id of the same shape, computed from its shards' ids, so merging the same shards again gives the same id and it differs from every shard's. The aggregated report of a workspace scan has an id of the form ASH-WORKSPACE-<workspace file name>-<date and time>-<hex digits>.

    Generating reports

    Of the 15 built-in reporters, 13 are enabled by default: csv, cyclonedx, flat-json, github-ghas, gitlab-cyclonedx, gitlab-sast, html, junitxml, markdown, ocsf, sarif, text, and unused-suppressions. spdx and yaml are available but disabled by default.

    To write only some of these reports, name them with --output-formats (short form -f), comma-separated, using the names in parentheses in the table above:

    ash scan --output-formats sarif,github-ghas,gitlab-sast

    To make the same choice for every scan, list the names under output_formats in your configuration file:

    # .ash/.ash.yaml
output_formats:
  - sarif
  - github-ghas

    output_formats also takes one name (output_formats: sarif) or names separated by commas, as --output-formats does; null means not set. A --output-formats list replaces the configured one for that run. With neither, every enabled reporter writes its report. ash merge --output-formats takes the same names, and without it ash merge uses the output_formats of the scan it merges.

    Either list narrows the enabled reporters; it does not turn on a reporter that is disabled. A name that produces no report, such as yaml while that reporter is disabled, is logged as an error that says why, and the scan continues. aggregated, dict, asff, and custom are accepted for compatibility but no reporter writes them. The AWS reporters (aws-security-hub, bedrock-summary-reporter, cloudwatch-logs, and s3) can be named the same way; they exist in a run only when ash_plugin_modules lists automated_security_helper.plugin_modules.ash_aws_plugins. A reporter from your own plugin module cannot be named in either list; it runs only when no list is given.

    To choose which reporters are enabled, use the reporters section in your configuration file:

    # ASH config file (.ashrc.yaml in a new project)
reporters:
  flat-json:
    enabled: true
  sarif:
    enabled: true
  html:
    enabled: false

    Reports are written to .ash/ash_output/reports/ by default.

    ASH does not write a report through a link. When the reports directory, a report file of an enabled reporter, a file a reporter writes beside its report (such as ash.unused-suppressions.md) or, in workspace mode, reports/workspace-reports.json is already a symlink or a directory junction, the run exits 1 before any reporter writes, and the error names the link. The reports directory is refused whether its link points to a directory or to nothing, before ASH creates or clears it. A fresh scan removes reports/ with anything in it before it starts, so a link left inside reports/ by an earlier run is cleared rather than refused. A workspace run is refused before any project is scanned, and container and nix mode exit 1 when a link is left in reports/ after the inner run. A regular file at one of those names is replaced as before. A reporter's report file name that is not a file in the reports directory (an extension with /, \ or .. that its config did not replace with the default), or such a name among the files a reporter writes beside its report, stops the run with exit 1 the same way, in container and nix mode too. There the inner run records the refusal in ash_inner_run_outcome.json beside ash_aggregated_results.json, and the outer process exits 1 with its message. The outer process reads the inner run's results back only when they carry a run_completed validation checkpoint with the ID it gave that run (ASH_OUTER_RUN_ID); otherwise it exits 1, saying the inner run did not complete.

    --use-existing exits 3 rather than report on a results file that holds no scan: one with neither scanner results nor findings, as a run that stopped before its scan recorded anything leaves, or one that records a refused run. Run the scan again without --use-existing.

    Each reporter writes files of its own. When two enabled reporters would write the same file, for example because reporters.cyclonedx.extension: sarif gives the CycloneDX report the SARIF report's name, the run exits 1 before either writes, and the error names both reporters and the file. Names are compared ignoring case and trailing dots and spaces, as case-insensitive file systems and Windows compare them. In workspace mode that covers reports/workspace-reports.json too, and the run is refused before any project is scanned.

    ash scan deletes the previous scan's results when it starts, as it always has, so a scan that fails leaves only what it wrote before it failed: gate CI on ASH's exit code, not on whether reports/ exists. Container and Nix mode delete them before they start the scan.

    A scan started over MCP keeps them until it has its own. When it starts, the MCP server moves the previous reports/, scanners/, analysis/, converted/, ash_aggregated_results.json, ash-ignore-report.txt and ash-scan-set-files-list.txt into .ash/ash_output/.ash_previous_results/. When the scan finishes they are deleted; when it fails or is cancelled, the server removes the results the scan had written, puts them back, and writes .ash_previous_results_restored beside them to say so. The scan's own logs, ash.log and ash.log.jsonl, stay. The next scan removes that file when it starts. A server that is killed outright cannot do any of this; the next MCP scan in the same output directory then treats .ash_previous_results/ as the last complete results, and the next ash scan deletes it. get_scan_progress for a scan whose previous results were put back returns output_holds_previous_results: true and no scanner data, because the files are not that scan's. The tools that read results from the directory (get_scan_results, get_scan_summary, get_scan_result_paths, explain_finding, diff_scan_results, suggest_suppression) answer that the scan is not complete, with output_holds_previous_results: true in the error's context.

    Flat JSON

    The flat-json format is ASH's native machine-readable output. It flattens the internal SARIF-based data model into a simple array of finding objects, making it straightforward to consume from scripts, dashboards, and downstream tooling.

    Schema overview

    The top-level structure contains four sections:

    {
  "metadata": { ... },
  "scanner_metrics": { ... },
  "top_hotspots": [ ... ],
  "findings": [ ... ]
}

    metadata -- report-level information: the project name (the configuration's project_name), scan time, report time, tool version and time delta.

    scanner_metrics -- a list of per-scanner objects with finding counts by severity and pass/fail status. Besides the counts, each object says what happened to the scanner:

    Field Description
    status PASSED, FAILED, ERROR, SKIPPED or MISSING
    excluded true when the run left the scanner out: --exclude-scanners or the shard split, --scanners, enabled: false in the configuration, --python-only, or a platform it does not support
    dependencies_missing true on a MISSING row, and only there, except a MISSING row for a scanner whose filtering raised before any dependency was checked (false; its missing_reason says so)
    missing_reason On a MISSING row, why: the tool that was not found, the reason the scanner's dependency check gave, or that the scanner could not be sandboxed. null otherwise
    skipped_reason On a SKIPPED row, why: which of the options above left it out, or that it had nothing to scan (for example no CloudFormation template for cdk-nag and cfn-nag, no lockfile for npm-audit), whether or not its tool is installed. null otherwise

    The scanner rows in ash_aggregated_results.json (scanner_results) carry the same status, excluded, missing_reason and skipped_reason, with dependencies_satisfied (false on a MISSING row, except one for a scanner whose filtering raised before any dependency was checked) and exit_code: the exit code of the scanner's tool, the highest over the targets it ran on, or null when no tool ran (a MISSING or excluded scanner, one that had nothing to scan, or one that started no tool for its targets, such as npm-audit with a yarn.lock and no yarn).

    top_hotspots -- the files with the most findings, ranked by count.

    findings -- an array of FlatVulnerability objects (described below).

    Finding fields

    Each object in the findings array has these fields:

    Field Type Description
    id string <scanner>-<rule>-<12 hex digits>, for example bandit-B105-0f3a9c21d4e7. The digits are a hash of the finding's identity: its SARIF fingerprints when the scanner reports ones that tell findings apart, otherwise its file (relative to the scan root) and its start and end lines; plus its package name and path for a dependency finding and its project in a workspace scan. A fingerprint the scanner writes on every result, such as semgrep's requires login, or one that findings of one scanner and rule share at different places in one file, does not count; the same value in another file or from another scanner still counts. A file a converter wrote, such as a converted notebook, is identified by its path under the converted files, so the id does not depend on where the output directory is. Findings that share all of that, such as two secrets on one line, are told apart by a digest of their column and message, so a newcomer does not take an existing finding's id and fixing one does not hand its id to another; only exact duplicates, with the same column and message, are numbered, the first keeping the plain id. A finding alone with its identity has no digest, so it keeps its id when the scanner rewords its message, and gets a new one when a second finding with the same identity appears. A finding identified by its lines gets a new id when an edit above it moves it; one with fingerprints keeps it. Upgrading a package to another vulnerable version keeps it
    title string Rule ID or short name of the finding
    description string Human-readable explanation of the issue
    severity string One of CRITICAL, HIGH, MEDIUM, LOW, INFO
    scanner string Name of the scanner that produced the finding (e.g., bandit, checkov)
    scanner_type string Category of scanner: SAST, SCA, IAC, SECRETS, SBOM, or UNKNOWN
    rule_id string or null The scanner-specific rule identifier
    file_path string or null Path to the affected file, relative to the scan root
    line_start integer or null First line of the finding, 1-based. The same value SARIF reports as region.startLine for that finding, so the two outputs can be cross-referenced
    line_end integer or null Last line of the finding, 1-based. Matches SARIF's region.endLine
    cve_id string or null CVE identifier, if applicable
    cwe_id string or null CWE identifier, if applicable
    fix_available boolean or null Whether a known fix exists
    is_suppressed boolean true if the finding was suppressed via configuration or inline annotation, including by an entry an MCP client's config supplied (see SARIF)
    suppression_kind string or null "inSource" or "external", depending on how it was suppressed
    suppression_justification string or null Reason text provided with the suppression
    detected_at string or null ISO 8601 timestamp of detection
    code_snippet string or null Relevant source code fragment. May span more lines than line_start–line_end when the scanner supplied surrounding context, so do not use it to infer the line range. Lines a secret finding reports are masked; see Secret values in reports
    tags string or null JSON-encoded array of tags
    properties string or null JSON-encoded map of additional scanner-specific properties
    references string or null JSON-encoded array of reference URIs
    raw_data string or null Full SARIF result object as a JSON string, after secret masking (see Secret values in reports)

    Consuming flat-json with jq

    # Count findings by severity
jq '[.findings[] | .severity] | group_by(.) | map({(.[0]): length}) | add' ash.flat.json

# List all HIGH and CRITICAL findings with file paths
jq '.findings[] | select(.severity == "HIGH" or .severity == "CRITICAL") | {title, file_path, line_start}' ash.flat.json

# Show only unsuppressed findings
jq '[.findings[] | select(.is_suppressed == false)]' ash.flat.json

# Get the top 5 files by finding count
jq '[.findings[] | .file_path] | group_by(.) | map({file: .[0], count: length}) | sort_by(-.count) | .[0:5]' ash.flat.json

    Consuming flat-json with Python

    import json
from pathlib import Path

report = json.loads(Path(".ash/ash_output/reports/ash.flat.json").read_text())

# Metadata
metadata = report["metadata"]
print(f"Project: {metadata['project']}, Tool: {metadata['tool_version']}")

# Scanner results
for scanner in report["scanner_metrics"]:
    print(
        f"{scanner['scanner_name']}: {scanner['status']} ({scanner['actionable']} actionable)"
    )

# Filter to actionable HIGH findings
high_findings = [
    f
    for f in report["findings"]
    if f["severity"] == "HIGH" and not f.get("is_suppressed", False)
]

for finding in high_findings:
    print(
        f"  {finding['file_path']}:{finding.get('line_start', '?')} - {finding['description']}"
    )

    SARIF

    SARIF (Static Analysis Results Interchange Format) is an OASIS standard for static analysis output. ASH produces SARIF 2.1.0 reports that work with GitHub Code Scanning, Azure DevOps, VS Code SARIF Viewer, and other tools in the SARIF ecosystem.

    The SARIF report is ASH's internal canonical representation -- all other formats are derived from it.

    The run's tool.driver is ASH, with ASH's version, and each scanner is a tool.extensions[] entry with its own name, version and rules (one run per project in workspace mode). Each result points at its rule in its scanner's extension, as SARIF 2.1.0 asks when rules are defined in an extension (3.27.7): rule.toolComponent names the extension and gives its index in tool.extensions, and rule.index is the rule's position in that extension's rules. A result whose rule no extension defines has no rule reference. Each scanner's version is the scanner's own: the version of its extension, and properties.scanner_version and properties.scanner_details.tool_version on each of its results. When ASH does not know a scanner's version, those fields are left out.

    Configuration: 

    reporters:
  sarif:
    enabled: true

    Output file: reports/ash.sarif

    Suppressions from an MCP client's config

    When the suppression, ignore path or scanner exclusion that hid a finding came from a config an MCP client delivered, the finding's SARIF suppression is marked: its justification starts with (ASH, client-supplied config) and names the entry, its kind is inSource for a suppression entry and external for an ignore path or a scanner exclusion, and it carries properties.clientSupplied: true:

    "suppressions": [
  {
    "kind": "external",
    "justification": "(ASH, client-supplied config) Ignoring finding under ignore path 'vendor/**' with reason: third-party code",
    "properties": {"clientSupplied": true}
  }
]

    The flat-json and CSV reports show such a finding with is_suppressed: true and that justification in suppression_justification. See Suppressions an MCP client's config supplied.

    CycloneDX

    CycloneDX is an OWASP standard for Software Bill of Materials. ASH produces CycloneDX 1.6 JSON documents that inventory dependencies and their known vulnerabilities. Use this format for SBOM compliance workflows and supply-chain security tools.

    The components come from the SBOM scanner, syft. When no SBOM scanner ran, for example because syft is not installed or --scanners left it out, the report is still a valid CycloneDX document, with an empty components list and a compositions entry whose aggregate is unknown, which tells a consumer that the inventory's completeness is not known rather than that the project has no dependencies: {"bomFormat":"CycloneDX","specVersion":"1.6","version":1,"components":[],"compositions":[{"aggregate":"unknown"}]}. The gitlab-cyclonedx report writes an empty component list in GitLab's format.

    Configuration: 

    reporters:
  cyclonedx:
    enabled: true

    Output file: reports/ash.cdx.json

    SPDX

    SPDX (Software Package Data Exchange) is a Linux Foundation standard focused on license compliance and software composition.

    The SPDX reporter is disabled by default. It writes an SPDX 2.3 JSON document built from the scan's CycloneDX SBOM, so both reports list the same components. The document describes a root package for the scanned project, which contains one package per SBOM component, with its version, its purl as an external reference, and its declared license when the SBOM gives an SPDX license ID or expression. Fields ASH cannot know, such as download location, concluded license and copyright text, are NOASSERTION. With no SBOM scanner in the run, the document contains only the root package.

    Configuration: 

    reporters:
  spdx:
    enabled: true  # disabled by default

    Output file: reports/ash.spdx.json

    OCSF

    OCSF (Open Cybersecurity Schema Framework) is a vendor-agnostic schema for security telemetry. The OCSF reporter transforms ASH findings into OCSF Vulnerability Finding events, suitable for ingestion into security data lakes and SIEM platforms like Amazon Security Lake.

    Configuration: 

    reporters:
  ocsf:
    enabled: true

    Output file: reports/ash.ocsf.json

    GitLab SAST

    The GitLab SAST reporter produces output compatible with GitLab's SAST report artifact, allowing findings to appear in the GitLab Security Dashboard and merge request widgets.

    Configuration: 

    reporters:
  gitlab-sast:
    enabled: true

    Output file: reports/ash.gl-sast-report.json

    GitLab CI example:

    ash-scan:
  stage: test
  script:
    - ash scan --source-dir . --output-dir ash_output
  artifacts:
    reports:
      sast: ash_output/reports/ash.gl-sast-report.json

    JUnit XML

    The JUnit XML reporter maps each scanner to a test suite and each finding to a test case failure. CI/CD systems (Jenkins, GitHub Actions, GitLab CI, Azure DevOps) can parse this format natively to display scan results alongside unit test results.

    Configuration: 

    reporters:
  junitxml:
    enabled: true

    Output file: reports/ash.junit.xml

    CSV

    Comma-separated values output for importing findings into spreadsheets or data pipelines. Each row represents one finding with columns for scanner, file path, line number, severity, rule ID, description, and suppression status.

    Configuration: 

    reporters:
  csv:
    enabled: true

    Output file: reports/ash.csv

    HTML

    An interactive single-file HTML report that can be opened in any browser. Includes sortable tables, severity filters, and per-scanner breakdowns.

    Configuration: 

    reporters:
  html:
    enabled: true

    Output file: reports/ash.html

    Markdown

    A Markdown summary suitable for embedding in pull request descriptions, README files, or documentation sites.

    Configuration: 

    reporters:
  markdown:
    enabled: true
    options:
      include_detailed_findings: true

    Output file: reports/ash.summary.md

    The scan metadata section has an Ignore files line: how many files the scanned repository's .gitignore and .ignore files excluded from ASH's scan set, or that they were not honored. It is left out in compact mode, with the rest of the scan metadata. See Ignore files and the scan set.

    YAML

    Structured findings in YAML format for human review or consumption by tools that prefer YAML over JSON.

    Configuration: 

    reporters:
  yaml:
    enabled: true

    Output file: reports/ash.yaml

    Text

    A plain-text summary written to the console and to a file. This is the format you see printed at the end of every scan.

    Configuration: 

    reporters:
  text:
    enabled: true

    Output file: reports/ash.summary.txt

    SCAN METADATA has the same Ignore files: line as the Markdown summary.

    Completeness fields

    ash_aggregated_results.json records why a scan is incomplete, and the exit code is decided from these fields:

    • scanner_results.<name>.missing_reason: why a MISSING scanner did not run when that was its tool being found only inside the scanned directory; it names the path. The YAML reporter and ash report --format yaml print it on every scanner row, null where it does not apply.
    • converter_results.<name>.failed_inputs: each input the converter could not convert, with path and reason.
    • In workspace mode, each project's incomplete_converters lists the converters that did not process their inputs, next to incomplete_scanners.

    Secret values in reports

    A finding can carry the value it found: bandit's B105, B106 and B107 quote it in their message, ferret-scan quotes it with show_match on, and every scanner's snippets (region.snippet and contextRegion.snippet) hold the lines around a finding, which can include a secret on a neighboring line. ASH masks these values once, after the scanners' results are merged and before ash_aggregated_results.json is written or any reporter runs, so every format above, the Bedrock summary and MCP responses get the masked results:

    • By location. Each snippet line, in any finding, at a file and line that a secret finding reports is replaced with [masked: a secret finding reports this line]. Its indentation and line ending are kept. Lines are counted the way scanners count them, at \n, \r\n and \r. A snippet in a file with a secret finding is masked whole when its line numbers are unknown, or when it holds a character only some line counts break at (a form feed, a vertical tab, NEL, U+2028, U+2029, an information separator or a lone \r), since its lines cannot be placed. A base64 (binary) snippet at a reported line is dropped.
    • By value. Each value a secret finding exposes is masked in its own message. That is the value its message quotes (Possible hardcoded password: '...', Matched text: '...', to the last quote of the message), or, for a finding that quotes none, what its own region matched (semgrep's and opengrep's columns). A value that looks like a secret is also masked wherever it occurs as a whole token in what any finding reports: messages, snippets, the other fields of a result and of additional_reports, including on lines no secret finding reports. Rule metadata, tags and identifiers (rule IDs, URIs) are left as they are. A value looks like a secret when it has at least eight characters, is not made of letters alone (one word, or words joined by spaces, dots, hyphens or underscores), is not a template placeholder such as ${NAME} or {name}, and is not repetitive (at least 2.5 bits of entropy per character). A hard-coded password check quotes ordinary words such as password as often as credentials, so a value that does not look like a secret is masked only in its own finding and in the findings that overlap it: those whose region or context, in the same file, covers a line the secret finding reports (or gives a snippet with no line number, or is in a file where the secret finding gives none). There every field is masked, messages and properties included, whatever the value's length or entropy. A short or all-letter secret is therefore left as it is in a finding on another line or in another file, where only masking by location applies. The masked form keeps at most the first two and the last character, for example hu*************t.

    A secret finding is one from a secrets scanner (detect-secrets, ferret-scan, gitleaks, or a result tagged tool_type::SECRETS), one tagged secret or secrets, a bandit B105, B106 or B107, a checkov CKV_SECRET_* rule, a rule with a secrets segment in its id (semgrep's and opengrep's generic.secrets.*), or a rule whose tags, in the tool's rule metadata or on the result, carry secret, secrets or a hard-coded credential CWE: CWE-798, CWE-259 or CWE-321. So is a rule about a credential written into infrastructure code, recognized by what its message or description says since neither tool tags these: checkov's "hard-coded" checks (CKV_AWS_41, CKV_AWS_45, CKV_AWS_46, CKV_AWS_384, CKV_AZURE_45, CKV_AZURE_131 and the providers' token and key checks) and cfn-nag's "... password must not be a plaintext string" rules (F23, F31, F34 and the rest). checkov puts the whole resource in each finding's snippet, so its lines are masked in every finding about that resource. cfn-nag reports only the resource's first line, so the masked range runs from there to the end of the file. Snippets with no secret in them are left as they were.

    Results that are read back from an existing ash_aggregated_results.json are masked the same way as they are loaded, whatever wrote the file (an older ASH, or another tool): ash report, ash scan --use-existing, ash merge, the MCP tools that read stored results (explain_finding, diff_scan_results, get_scan_results), the findings browser and a workspace's unified reports. For a finding with no snippet, the findings browser shows the lines around it read from the file on disk, and masks them the same way: lines a secret finding reports, and every value the results' masking found.

    Masking also crosses result sets. ash merge masks the merged results by location against the secret findings of every shard, since a secret one shard's scanner reports can sit in another shard's snippets. A value is harder: each shard was masked in its own process, and none holds the value any more. So every results file records, under secret_value_shapes, the shape of each value it masked: the visible prefix, the visible suffix and the length, which the masked form already shows. The value itself, or a digest of it, is never written. ash merge masks every whole token of one of those shapes in every shard, and so does every later reading of a results file that records shapes. Masking by shape is approximate: a different token with the same visible characters and the same length is masked too.

    A workspace scan masks each project against its own findings while the project runs. Once every project has finished, it masks each project's results file and reports under projects/<key>/, and the unified results, again with the values every project's secret findings exposed, so a value one project reports is masked where another project's finding shows it. A project abandoned at its project_timeout contributes no values.

    The scanner's own output files under scanners/<name>/ are what the tool wrote, and are not masked.

    Relationship between formats

                        ┌─────────────────────┐
                    │  Scanner outputs     │
                    │  (bandit, checkov,   │
                    │   semgrep, ...)      │
                    └─────────┬───────────┘
                              │
                              ▼
                    ┌─────────────────────┐
                    │  SARIF (canonical)   │
                    │  ash.sarif           │
                    └─────────┬───────────┘
                              │
              ┌───────────────┼───────────────┐
              │               │               │
              ▼               ▼               ▼
        ┌───────────┐  ┌───────────┐  ┌───────────┐
        │ Flat JSON  │  │ CycloneDX │  │ HTML/MD/  │
        │ OCSF      │  │ SPDX      │  │ CSV/Text  │
        │ GitLab    │  │           │  │ YAML      │
        │ JUnit XML │  │           │  │           │
        └───────────┘  └───────────┘  └───────────┘

    All reporters read from the same internal AshAggregatedResults model. SARIF is the primary interchange format; the flat-json reporter flattens the SARIF data into a simpler structure, while CycloneDX and SPDX focus on the software-composition subset. The human-readable formats (HTML, Markdown, Text) and tabular formats (CSV, JUnit XML) present the same underlying data in different layouts.

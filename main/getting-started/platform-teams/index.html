    Roll out ASH across repositories¶

    This tutorial is for a security or platform team that runs ASH for many repositories. By the end you have an ASH image in your own registry, one operator config that every scan uses and no repository can change, a plan for keeping vulnerability databases current, and results going where your team reads them.

    Before you start¶

    You need ASH installed (Install ASH), docker or another container runtime, and a registry you can push to. Steps 2 and 3 run on any machine with ASH, and step 3 creates a small repository to test the gate on.

    1. Build the image and push it to your registry¶

    ASH publishes no prebuilt image. Build one from v3.7.0, name it for your registry, and push it:

    export ASH_IMAGE_NAME=registry.example.com/security/ash:3.7.0
ash build-image --no-run --oci-runner docker --ash-revision-to-install v3.7.0 \
  --container-uid 1001 --container-gid 1001
docker push "$ASH_IMAGE_NAME"

    You should see Building image registry.example.com/security/ash:3.7.0, a few minutes of build output, and then the push. --oci-runner docker builds with the runtime you push with; without it, ASH uses finch when finch is installed. The image holds every scanner tool and runs as a non-root user with the UID and GID you passed; use the ones your CI jobs run as. A build host that runs as root needs --build-target ci, because ASH refuses to build the non-root image as UID 0; see Root and non-root images.

    2. Write the operator config¶

    The operator config is the one file whose settings apply to every scan. Keep it where only your team can change it, outside the directories you scan and outside every git checkout, including an operations repository and a home directory or /etc kept in git. ASH treats a config file inside any git checkout, or inside the directory it scans, as written by a repository, even when you name it with --config, and ignores the settings in it that only an operator may make, such as sandbox grants and the AWS reporters' destinations and credentials. Such a config can turn on plugin modules that are already installed outside every git checkout and the scanned directory, such as in site-packages. It can't load plugin code from the repository or any other checkout, load ash_aws_plugins or ash_snyk_plugins unless an operator source names them, or turn on a reporter that sends findings off the host. It logs that only to ash.log, and the warning says how to keep the setting: put it in a config file outside every git checkout and the scanned directory, or pass it with --config-overrides (Configuration trust model). This tutorial uses $HOME/ash-operator/ash.yaml; on shared runners, a path such as /etc/ash/ash.yaml is a better choice.

    OPERATOR_CONFIG="$HOME/ash-operator/ash.yaml"
mkdir -p "$(dirname "$OPERATOR_CONFIG")"
cat > "$OPERATOR_CONFIG" <<'EOF'
fail_on_findings: true
fail_on_incomplete_scanners: true
content_db_staleness: fail
global_settings:
  severity_threshold: MEDIUM
EOF
if git -C "$(dirname "$OPERATOR_CONFIG")" rev-parse --is-inside-work-tree >/dev/null 2>&1; then
  echo "The operator config is inside a git checkout; move it." >&2
  exit 1
fi

    The last three lines check that the file is in no git checkout: git rev-parse must fail there. That is the rule ASH applies to config files, and the check catches a file it would treat as a repository's before any scan warns about it, for example under a home directory kept in git. The four settings are the gate: fail on findings at MEDIUM or above, fail when a scanner was MISSING or ended in ERROR, and fail when a vulnerability database or offline ruleset is past its age bound. They are also ASH's defaults, and writing them down still matters: with this file in use, ASH does not read a repository's config file, so the repository cannot change them. Add your organization's suppressions, scanner options, and reporters to the same file; Configure ASH shows how.

    3. Check that a repository cannot change the gate¶

    Create a repository with one hardcoded password in it:

    mkdir ash-gate-demo
cd ash-gate-demo
git init --quiet
printf 'DATABASE_PASSWORD = "correct-horse-battery-staple-1234"\n' > app.py

    Scan it with the operator config:

    ash scan --config "$OPERATOR_CONFIG" --scanners detect-secrets

    --scanners detect-secrets keeps the check fast: detect-secrets ships with ASH, so it needs no other tools. The scan ends with ERROR (2) Exiting due to 1 actionable findings found in ASH scan. Once the scan has loaded a config file, .ash/ash_output/ash.log names it in a Using ASH configuration from line. A file you name with --config appears as you named it:

    grep -F "Using ASH configuration from $OPERATOR_CONFIG" .ash/ash_output/ash.log

    Now give the repository a config file that turns the gate off, and scan without your config:

    printf 'fail_on_findings: false\n' > .ashrc.yaml
ash scan --scanners detect-secrets

    ash.log now names the repository's file. A file ASH finds on its own appears by its resolved path, with every symbolic link followed, so the check uses pwd -P:

    grep -F "Using ASH configuration from $(pwd -P)/.ashrc.yaml" .ash/ash_output/ash.log

    The scan exits 0 although the finding is still there. Scan again with your config:

    ash scan --config "$OPERATOR_CONFIG" --scanners detect-secrets

    The scan exits 2 again, because ASH read only your file.

    In a scan of one directory, when you pass --config or set ASH_CONFIG, ASH does not read the repository's config file at all, so a repository cannot turn off the gate, raise the threshold, disable scanners, or add suppressions through it. In workspace mode, your --config is layered over each project's own config: every setting your file makes is final for every project, and a project's config fills only the settings yours leaves out (Scan a multi-project workspace). That holds for the settings only an operator may make, such as sandbox grants and the AWS reporters' destinations, only while your file is outside every git checkout; inside one, the plugin modules it may add are limited the same way as a repository's.

    The repository can still affect results in other ways:

    • Inline ash-ignore comments, which ASH honors and marks (ASH inline) in the SARIF report.
    • The scanners' own inline suppressions, such as bandit's # nosec and detect-secrets' # pragma: allowlist secret. To have bandit report # nosec lines too, set scanners.bandit.options.ignore_nosec: true in your file.
    • Its .gitignore and .ignore files, which decide which files ASH scans, committed files included.
    • The tool config files some scanners read from the repository, such as detect-secrets' .secrets.baseline, whose plugin and filter settings apply unless your file sets scanners.detect-secrets.options.scan_settings.plugins_used. What the trust model does not protect lists the scanners whose own config files ASH keeps from being read, semgrep's and opengrep's .semgrepignore included.

    When you let ASH read a repository's config file instead, that file can change the verdict, but it cannot load ASH's plugin packages that send data off the machine, choose reporter destinations or credentials, grant sandbox access, or set the scanner options in Options only the operator can set. Configuration trust model has the complete rules.

    4. Run the scan in CI¶

    In CI, run ASH inside your image, mount the repository and the operator config, and point ASH_CONFIG at the config:

    test -f /etc/ash/ash.yaml
mkdir -p "$PWD/../ash-results"
docker run --rm \
  --mount type=bind,source="$PWD",destination=/src,readonly \
  --mount type=bind,source="$PWD/../ash-results",destination=/out \
  --mount type=bind,source=/etc/ash/ash.yaml,destination=/etc/ash/ash.yaml,readonly \
  --env ASH_CONFIG=/etc/ash/ash.yaml \
  registry.example.com/security/ash:3.7.0 \
  ash scan --source-dir /src --output-dir /out

    The test -f line stops the job before docker run when the operator config is missing. ASH inside the container refuses an ASH_CONFIG that names no file too, with exit code 3, instead of scanning with the defaults. The repository is mounted read-only, and the results go to a directory outside it. The job fails with exit code 2 on findings and 1 on an incomplete scan; Exit codes lists them all.

    ash scan --mode container --no-build, with ASH_IMAGE_NAME naming your image, works too. Container mode mounts your --config file read-only for the scan inside the container (The config file). The CI guides show the same setup for each service: Run ASH in GitHub Actions, Run ASH in GitLab CI, and Run ASH in Jenkins, CodeBuild, Azure Pipelines, CircleCI, and other CI systems.

    5. Plan content database refresh¶

    grype and trivy check code against vulnerability databases, and ASH fails a scan when a database is past its age bound. An image that scans online refreshes the trivy database during each scan, and grype updates its own database, so the hosts need outbound access to the databases' download sites. An offline image carries the databases it downloaded at build time. trivy's bound is the shortest, a day, and it counts from when the database was built upstream, which is before your image build. An offline image holds trivy's database to warn, so its trivy scans keep passing after that day and the reports record the stale database. grype's bound is five days, and past it the scan fails.

    An offline image cannot run npm-audit, because npm, yarn, and pnpm audit a lockfile by asking the registry. A scan with it reports npm-audit MISSING, and exits 1, for a project with a lockfile beside its package.json. Add --exclude-scanners npm-audit to the scan command for those projects, or scan them with an online image.

    An offline build downloads current databases once per UTC day even without --force, but only --force keeps the build from reusing the cached layers that hold the old tools, so rebuild the image on a schedule with it:

    ash build-image --no-run --force --oci-runner docker --ash-revision-to-install v3.7.0 \
  --container-uid 1001 --container-gid 1001
docker push "$ASH_IMAGE_NAME"

    If the rebuild runs in a CI job that runs as root, as AWS CodeBuild and container-based GitLab and Jenkins jobs do, pass --build-target ci: ASH refuses to build the non-root image as UID 0. Rebuild offline images more often than every five days, because grype's bound also counts from the database's upstream build, and more often still to keep trivy's findings current. Rebuild online images at least weekly, so the scanner tools get their fixes. Keep content_db_staleness: fail in the operator config; a repository cannot relax it while you pass --config. To hold trivy's database to its bound in an offline image too, also set content_db_staleness_offline_image_default: false. Run ASH offline covers air-gapped hosts, and Content databases lists every bound.

    6. Send findings where your team reads them¶

    Every scan writes its reports to reports/ in the output directory. Send each to the place your team works:

    • GitHub code scanning: upload ash.ghas.sarif (Export reports).
    • GitLab security dashboards: publish ash.gl-sast-report.json as a SAST report from a job that succeeds, because GitLab ingests security findings only from successful jobs (Run ASH in GitLab CI).

    • A central store or SIEM: copy a findings file, such as ash.ocsf.json or ash.sarif, with your own tooling:

      aws s3 cp ../ash-results/reports/ash.ocsf.json \
  "s3://example-security-scan-results/$REPOSITORY_NAME/$(date -u +%Y%m%dT%H%M%SZ).ocsf.json"

    • AWS services: ASH's AWS reporters are loaded by the operator only. The S3 and CloudWatch Logs reporters send the scan summary and configuration, not individual findings; read AWS reporters for what each one sends before you turn it on.

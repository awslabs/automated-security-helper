    Scanner facets reference¶

    This page is generated from the scanner facets register in the ASH source code by scripts/generate_facets_reference.py. Edits made to this file by hand are overwritten the next time it is generated.

    ASH ships 23 scanners, and every one declares, per facet of the shared vocabulary, whether its native output maps into the shared pipeline. The register is production code (automated_security_helper/base/scanner_facets.py): the declaration has runtime consumers, and a scanner without one is refused by the registry totality test. The four states:

    • mapped: the facet lands where the shared pipeline reads it, and the cell names the native field it comes from. The corpus-consistency gate (tests/unit/plugin_modules/test_scanner_facets_corpus_consistency.py) holds these cells against the committed fixtures.
    • mappable-dropped: the native output carries the value and ASH discards it today: a roadmap record, not a promise. The cell names the native field and why it is dropped.
    • n/a: this scanner class cannot have the facet, with the reason. The corpus gate treats a populated column here as contamination.
    • unconfirmed: no real run of the tool has been read for the facet, so the register claims neither that it maps nor that it cannot exist. The cell says what was read instead and the run that would settle it. The corpus gate lists it as a fixture owed and fails nothing.

    The facet vocabulary, in declaration order: rule_id, severity, file_path, line_range, column, message, resource_id, resource_type, package_name, package_version, package_path, taxonomy_cve, taxonomy_cwe, fingerprints, fix_available, remediation_text, snippet, references, tags, extras.

    Runtime compatibility¶

    Some tool versions do not run on some versions of the language runtime they are installed into. The operational register (automated_security_helper/base/scanner_operational_facets.py) records each known case as a row on the scanner's runtime_compat facet: a range of tool versions, the range of runtime versions it needs, and the reason, measured. The installer derives the interpreter it asks uv for from these rows, so there is one place a range is declared.

    Ranges are written in the grammar native to the runtime: python uses PEP 440 specifier set (packaging.specifiers.SpecifierSet); node uses node-semver comparator ranges (validator not yet landed). An empty tool range means every version of the tool.

    • pin: the interpreter request is constrained to the runtime range. The preferred resolution.
    • polyfill: a shim is applied over the runtime range at tool launch. A polyfill row states why a pin cannot serve.
    • open-ended: the incompatibility is unsolved upstream. The row declares only the bounds that are proved, links the upstream issue (or says what was searched when none exists to cite), and is re-read whenever the tool's version constraint moves.
    Scanner Runtime Tool versions Runtime request Resolution Open-ended Reason
    checkov python all >=3.10,<3.15 pin yes, https://github.com/bridgecrewio/checkov/issues/7777 CPython 3.15 made array_hook a required argument of json.decoder.JSONArray (signature 3.14.9: (s_and_end, scan_once, _w, _ws); 3.15.0: (s_and_end, scan_once, array_hook, _w, _ws)); checkov's Decoder.json_array (checkov/common/parsers/json/decoder.py) calls it without one, so every JSON document that holds an array fails to parse, and on a large tree the parallel runner can wait indefinitely on the worker error; reported against checkov 3.4.3 and 3.4.0 on 3.15.0; a fix is proposed upstream in bridgecrewio/checkov#7778 and not merged
    guarddog python all >=3.10,<3.14 pin yes, no upstream issue exists to cite: a search of the VirusTotal/yara-python issues for a cp314 report found none (a 'wheel' search returned issues, so the search itself works; read 2026-11-25); re-check pygit2 and yara-python cp314 wheels at the next guarddog version bump pygit2 1.18 and yara-python 4.5 publish no CPython 3.14 wheels at the pinned guarddog==3.2.0, so on a host where uv would pick 3.14 the install builds them from source, which needs libgit2 headers and a C toolchain, and fails; measured with uv 0.12 on Linux x86_64: an unconstrained 'uv tool install guarddog==3.2.0' picked 3.14 and failed on pygit2, and with --python '>=3.10,<3.14' it installed; PyPI read 2026-11-25: pygit2 publishes cp314 wheels from 1.19.0, while yara-python publishes none through 4.5.4

    2 of 23 scanners declare a row. The other 21 declare none: no incompatibility between their tool versions and their runtime versions is known.
